# 커밋 메시지 작성 지침

## 적용 범위

- Git 커밋 메시지를 작성·제안·검토할 때 적용한다.

## 작성 기준

- 제목과 본문은 한국어로 작성한다. API 이름, 식별자, 패키지 이름 등 고유 명칭은 원문을 유지한다.
- 제목과 본문은 완결된 서술문 대신 간결한 구 형태로 작성한다. `추가한다`, `수정했습니다` 대신 `추가`, `수정`, `유지`처럼 표현하고 문장 끝 마침표는 붙이지 않는다.
- `feat:`, `fix:`, `docs:` 등의 유형 접두사를 붙이지 않는다.
- 실제 커밋 대상 변경을 확인하고 작성한다. 커밋 대상은 스테이징된 변경을 기준으로 하며, 스테이징되지 않은 변경이나 다른 이슈의 내용을 섞지 않는다.
- 스테이징 전 메시지를 제안하는 경우 명시된 변경 범위를 기준으로 작성하고, 실제 커밋 전 스테이징된 변경과 일치하는지 다시 확인한다.
- 계획이나 미완료 작업을 완료한 것처럼 표현하지 않는다. 변경 범위를 확인할 수 없으면 추측으로 메시지를 만들지 않고 필요한 정보를 확인한다.

## 제목

- 변경 사항의 핵심을 간결하고 구체적인 한 줄 주제로 작성한다.
- 무엇을 추가·수정·변경했는지 드러내고, `수정`, `작업 완료`, `코드 개선`처럼 대상과 내용이 불명확한 제목을 피한다.
- 파일 목록을 나열하기보다 변경의 목적이나 동작을 설명한다.

## 본문

- 제목만으로 충분하면 본문을 형식적으로 추가하지 않는다.
- 본문이 필요하면 제목 다음에 빈 줄을 두고, 변경 이유와 주요 내용을 `- `로 시작하는 목록으로 기록한다.
- 각 항목은 하나의 핵심 내용을 간결하게 표현한다. 내용 구분이 필요하면 목록 묶음 사이에 빈 줄을 둔다.
- 호환성 영향, 설정 변경이나 마이그레이션 등 주의사항이 있으면 명시한다.
- 검증 결과를 적을 때는 실제 수행한 검증과 결과만 기록한다. 실행하지 못했거나 실패한 검증을 통과했다고 쓰지 않는다.
- 이슈 문서 전체나 작업 히스토리를 복사하지 않고 커밋 이해에 필요한 내용을 요약한다.

## 이슈 참조

- 관련 이슈가 있으면 본문 목록에 원본 번호 또는 이슈 키와 원본 URL을 기록한다. 숫자 번호만으로 출처를 단정하지 않는다.
- 여러 이슈가 실제 변경과 관련되면 각각 연결하고, 무관한 이슈를 포함하지 않는다.
- 명시적인 이슈 종료 요청이 없으면 `Closes`, `Fixes`, `Resolves` 등 해당 시스템에서 자동 종료를 유발하는 구문을 사용하지 않는다. 일반 참조와 이슈 종료는 구분한다.

## 트레일러

- `Co-authored-by`, `Signed-off-by` 등 Git 트레일러의 키와 형식은 번역하지 않고 적용되는 저장소·작업 정책을 따른다.
- 트레일러는 본문 목록과 구분하며 앞에 `- `를 붙이지 않는다.
- 기여자 이름·이메일을 임의로 만들거나 실제로 확인되지 않은 서명·인증을 추가하지 않는다.
- 단독으로 작성한 커밋에는 커밋 작성자 본인을 `Co-authored-by`로 다시 추가하지 않는다.
- 공동 기여자가 있으면 별도 제외 요청이 없는 한 커밋 작성자를 제외한 실제 공동 기여자의 `Co-authored-by` 트레일러를 커밋 메시지 마지막에 포함한다. 에이전트가 공동 기여한 경우에도 실제 기여와 확인된 이름·이메일을 기준으로 한다. 기여자 정보를 확인할 수 없으면 임의로 만들지 않고 해당 사실을 보고한다.

## 작성 예시

아래는 공동 기여자가 있는 경우의 형식 예시이다. 실제 변경과 이슈에 맞게 작성하고, 예시 내용과 주소를 그대로 사용하지 않는다.

```text
요청 취소 시 응답 스트림 자원 해제

- 요청 취소 후 남은 응답 스트림 정리
- 기존 정상 응답 동작 유지

- 관련 이슈: PROJ-123
- 이슈 URL: https://tracker.example.com/browse/PROJ-123

Co-authored-by: 홍길동 <honggildong@example.com>
```
