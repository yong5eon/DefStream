# Markdown 작성 지침

## 문서 구조

- 일반 문서는 내용을 대표하는 최상위 제목 `#` 하나로 시작한다. YAML frontmatter가 필요한 지침 파일 등은 frontmatter를 먼저 두고 해당 형식을 유지한다.
- 제목 단계는 `#`, `##`, `###` 순서로 사용하고 불필요하게 건너뛰지 않는다. 제목은 짧고 구체적으로 작성한다.
- 목적과 핵심 내용을 먼저 두고 상세 설명, 참고 자료와 도구 설정은 뒤에 배치한다.
- 목차와 고정 섹션은 문서의 분량과 탐색 필요에 따라 사용한다. 모든 문서에 일률적으로 요구하지 않는다.

## 문장과 표현

- 한국어로 작성하되 API, 식별자와 제품명 등 고유 명칭은 원문을 유지한다.
- 설명은 명확한 문장으로, 목록과 표의 항목은 간결한 표현으로 작성한다. 커밋 메시지의 구 형태 작성 규칙을 일반 문서에 일률적으로 적용하지 않는다.
- 확인된 사실, 계획, 예시와 미확정 사항을 구분한다.
- 강조는 핵심 정보에 한정하고 장식용 이모지, 구분선과 과도한 강조는 지양한다.

## 목록과 표

- 순서 없는 목록은 `-`, 수행 순서가 있는 절차는 번호 목록을 사용한다.
- 같은 수준의 목록은 표현 형식을 일관되게 유지한다. 하위 목록은 상위 항목의 설명에 필요한 경우에만 사용한다.
- 비교나 정형 정보에는 표를 사용하되 긴 설명, 코드와 복잡한 절차는 표 밖으로 분리한다.
- 빈 항목이나 의미 없는 틀을 형식적으로 추가하지 않는다.

## 코드와 명령

- 코드 블록에는 가능한 경우 `python`, `javascript`, `json`, `shell`, `text` 등 내용에 맞는 언어를 표시한다.
- 마크다운의 코드 블록(소스 코드 등 텍스트 영역)에서는 탭 대신 공백 2개로 들여쓰기한다. 단, 실행 문법상 다른 들여쓰기가 필요하거나 외부 원문·실제 소스를 그대로 인용하는 경우에는 정확한 동작과 원형 보존을 우선한다.
- 파일명, 경로, 명령, 설정 키와 식별자는 인라인 코드로 구분한다. 파일이나 문서를 연결하는 경우에는 링크를 사용한다.
- 예시는 실제 공개 API와 설정에 맞게 작성한다. 생략한 부분이나 자리표시자가 있으면 명시하고 실행 가능한 완성 예시와 구분한다.
- 실행 명령에는 실행 위치, 필요한 환경과 주의사항을 필요한 범위에서 함께 설명한다.
- 실제 실행 결과와 예시 출력을 구분한다. 비밀값과 개인정보를 문서나 예시에 넣지 않는다.

## 링크와 자료

- 문서 내부의 파일 링크는 해당 문서를 기준으로 한 상대 경로를 사용한다. 외부 자료는 원본을 확인할 수 있는 URL로 연결한다.
- 링크 경로에는 운영체제와 관계없이 `/`를 사용한다.
- `여기`처럼 모호한 문구보다 연결 대상이 드러나는 링크 문구를 사용한다.
- 파일을 이동하거나 이름을 바꾸면 관련 링크와 필요한 제목 앵커를 함께 갱신한다.
- 이미지에는 내용을 이해할 수 있는 의미 있는 대체 텍스트를 제공한다.

## 분량과 유지보수

- 같은 상세 내용을 여러 문서에 복사하지 않고 기준 문서로 연결한다.
- 내용이 길어 분리할 때는 개요 문서에 각 세부 문서의 설명과 링크를 유지한다. 작업 기록 등 별도 분리 규칙이 있으면 해당 규칙을 따른다.
- 기존 문서의 구조와 관례를 존중하며 요청과 무관한 전체 재정렬이나 서식 변경은 하지 않는다.
- 줄 길이 제한이나 새 문서 생성을 일률적으로 강제하지 않고 가독성과 유지보수에 필요한 만큼만 적용한다.

## 작성 후 확인

- 제목 계층, 목록 들여쓰기, 코드 블록의 닫힘, 표와 링크가 올바른지 확인한다.
- 명령, 경로와 예시가 실제 프로젝트와 일치하는지 확인하며 수행하지 않은 검증을 완료한 것처럼 기록하지 않는다.
- 기존 Markdown 검사 도구나 문서 테스트가 있으면 변경 범위에 맞게 활용한다. 문서 작성을 위해 도구를 불필요하게 추가하지 않는다.
