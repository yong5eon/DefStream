# 역할과 전문성

- 객체 지향 프로그래밍(Object-Oriented Programming)과 객체 지향 설계(Object-Oriented Design)를 고려해 개발한다.

# 개발 원칙

## SRP (Single Responsibility Principle)

- 클래스, 함수, 모듈은 하나의 명확한 책임을 갖도록 설계한다.
- 서로 다른 이유로 변경되는 역할이나 관심사가 섞여 있다면 분리를 검토한다.
- 책임 분리는 이해와 변경을 쉽게 할 때 적용하고, 불필요한 추상화로 이어지지 않게 한다.

## YAGNI (You Aren't Gonna Need It)

- 현재 명시된 요구사항과 필요한 동작만 구현한다.
- 미래에 필요할 것이라는 추측만으로 기능, 설정, 매개변수, 인터페이스, 추상화를 추가하지 않는다.
- 기존 동작이나 계약을 변경해야 한다면 영향 범위를 확인하고 필요한 변경만 수행한다.

## KISS (Keep It Simple)

- 문제의 원인과 요구사항을 직접 해결하는 가장 명확하고 단순한 방법을 선택한다. 단순함은 코드 줄 수나 당장의 변경량만으로 판단하지 않으며, 문제를 회피하거나 증상만 숨기는 우회책을 단순한 해결로 취급하지 않는다.
- 제약 때문에 우회가 불가피하거나 명시적인 요구로 우회해야 한다면, 이유와 남는 영향·한계를 확인하고 드러낸다.
- 복잡한 추상화나 디자인 패턴은 실제로 문제를 단순화하는 경우에만 사용한다.
- 중복을 제거하는 것보다 이해하기 쉬운 코드가 중요하다면 명확한 중복을 허용한다.
- 함수 길이, 조건문 중첩, 매개변수 수 등은 절대 기준으로 제한하지 않는다. 복잡성이 이해와 변경을 어렵게 만드는지 판단하는 참고 신호로 사용한다.

## 구조와 호출 흐름

- 코드는 관련 책임이 응집된 모듈·클래스·함수로 구성하고, 각 책임의 소유자와 경계가 드러나도록 한다. 관련 없는 함수와 상태를 한곳에 무질서하게 나열하지 않는다.
- 객체 지향 설계를 적극 고려하되, 함수나 데이터를 형식적으로 클래스로 감싸지 않는다. 상태, 불변 조건, 생명주기 또는 협력하는 동작을 함께 소유하고 관리할 때 클래스를 사용하며, 독립적인 변환이나 계산은 자연스러운 형태로 둔다.
- 모듈·클래스·함수 사이의 호출은 각 단계가 맡은 책임과 데이터 흐름을 읽을 수 있게 유지한다. 인자와 결과를 거의 그대로 다음 함수에 전달하는 중계 사슬이나, 실질적인 책임 없이 호출만 위임하는 래퍼를 만들지 않는다.
- 중간 계층은 정책 적용, 의미 있는 변환, 경계 분리, 자원 관리 등 명확한 역할이 있을 때 둔다. 값을 전달하는 단계가 반복되면 해당 책임의 소유 위치와 호출 구조를 다시 검토한다.
- 함수·메소드 추출은 독립된 책임, 의미 있는 이름, 재사용 또는 흐름의 가독성을 높일 때 수행한다. 호출 단계를 늘리거나 함수 길이를 줄이기 위한 기계적인 분해는 피한다.
- 중첩과 분기는 정상 흐름과 예외 흐름을 구분해 읽을 수 있도록 구성한다. 불필요하게 깊은 중첩은 조기 반환 등으로 단순화하되, 조건 검증을 숨기거나 의미 없는 추상화로 옮기지 않는다.

## 적용 기준

- 세 원칙을 기계적인 순서나 절대 규칙으로 적용하지 않는다. 요구사항, 기존 코드의 계약, 가독성과 변경 용이성을 함께 고려한다.
- 요청 범위와 무관한 리팩터링은 피한다. 기능 변경과 구조 변경을 분리하는 것이 검증과 리뷰에 도움이 될 때 작은 단위로 수행한다.
- 작업 후에는 변경 범위와 위험에 맞는 테스트나 검증을 선택해 실행한다. 테스트 수나 실행 범위를 완전성의 대리 지표로 삼지 않는다.

## 테스트와 검증

- 테스트는 명시된 요구사항, 공개 동작, 인수 기준 또는 확인된 위험에 연결한다. 각 테스트가 확인하는 동작과 필요한 이유를 분명히 하고, 기존 테스트와 같은 동작을 중복 검증하거나 구현 세부사항에 불필요하게 결합하지 않는다.
- 변경 전 결함을 재현하거나 변경 후 회귀를 확인하는 테스트를 우선한다. 기존 테스트가 이미 동작을 충분히 보장하면 근거 없이 유사한 테스트를 추가하지 않는다.
- 테스트 실행은 변경과 가장 가까운 범위에서 시작한다. 관련 테스트가 통과하고 추가로 확인할 구체적인 위험이나 미해결 문제가 없으면 전체 테스트나 더 넓은 테스트로 연쇄 확장하지 않는다.
- 테스트 실패, 구체적인 불확실성 또는 변경 영향 범위가 더 넓다는 근거가 있을 때만 검증 범위를 확장한다. 확장할 때는 확인하려는 위험과 범위를 명확히 한다.
- 전체 테스트, 조합 테스트와 장시간 검증은 변경 영향이나 계약상 필요가 있을 때 수행한다. 시간과 비용이 큰 검증은 더 좁은 검증으로 충분한지 먼저 판단한다.
- 실제 실행한 테스트와 범위, 결과를 보고한다. 실행하지 않은 더 넓은 테스트를 통과한 것처럼 표현하지 않는다.

# 공통 코드 작성 규칙

- 언어별 명명 규칙, 포맷, 관용 패턴은 해당 언어의 세부 지침과 저장소의 기존 관례를 따른다.
- 주석, 문서, 개발 과정에서 사용자에게 제공하는 설명은 한국어로 작성한다. 코드 식별자와 외부 API·라이브러리의 고유 명칭은 번역하지 않고 원문과 해당 언어의 관례를 따른다.
- 새 클래스나 상속 관계를 다룰 때는 부모 클래스 또는 인터페이스의 계약과 시그니처를 확인한다. 외부 API나 타입이 불명확한 호출도 사용 전에 계약을 확인한다.
- 예상치 못한 오류를 조용히 무시하거나 성공한 것처럼 처리하지 않는다. 오류를 적절한 맥락과 함께 전파하거나 예외를 발생시킨다.
- 입력 검증과 방어적 검사는 신뢰할 수 없는 외부 입력이 들어오는 경계와 명시된 불변 조건에 집중한다. 이미 보장된 내부 조건을 여러 계층에서 반복 검사하거나, 포괄적인 예외 처리·임의 기본값으로 오류 또는 호출자가 기대한 예외를 숨기지 않는다.
- 폴백, 기본값, 더미 데이터는 명시된 요구사항이 있을 때만 사용한다. 오류를 숨기기 위한 대체 동작으로 사용하지 않는다.
- TODO는 지금 처리하지 않을 구체적인 작업이 남아 있을 때만 남기는 것을 권장한다. 가능한 경우 후속 작업을 식별할 수 있도록 내용을 구체적으로 작성한다.
- 요구사항이나 기존 계약과 지침이 충돌하면 임의로 계약을 깨지 않는다. 충돌과 영향 범위를 확인하고, 해결이 불명확하면 사용자에게 알린다.
