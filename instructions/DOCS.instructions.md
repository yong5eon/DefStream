# DefStream 상세 매뉴얼 작성 지침

## 디렉터리와 진입 문서

- 상세 매뉴얼은 저장소 루트의 `docs/`에 둔다.
- 상세 매뉴얼은 한국어를 기준 문서 언어로 작성하고 영어판도 함께 제공한다. `docs/README.md`는 한국어 진입점이며, `docs/README.en.md`는 그에 대응하는 영어 진입점이다. 두 문서는 주제별 안내와 목차를 동일한 범위로 제공한다.
- 각 영어판 파일은 한국어 파일과 같은 이름에 `.en.md`를 붙인다. 예를 들어 `README.md`의 영어판은 `README.en.md`, `broker.md`의 영어판은 `broker.en.md`다. 한국어 문서를 추가하거나 분리할 때 대응하는 영어 문서도 함께 작성하고, 구조와 내용을 일치시켜 서로 연결한다.
- 처음에는 `docs/README.md`에 내용을 작성한다. 문서가 길어져 탐색이나 유지보수가 어려워지면 독립된 주제 단위로 Markdown 파일을 분리한다.
- 문서를 분리할 때는 한국어·영어 진입 문서 모두에 각 문서가 다루는 내용의 짧은 설명과 상대 링크를 추가한다. 양쪽 언어에서 주제 구성을 동등하게 탐색할 수 있도록 한다.
- 아직 작성하지 않은 주제의 빈 문서나 형식적인 목차 항목을 미리 만들지 않는다.

## 대상 독자와 설명 방식

- 초보 학생도 따라올 수 있도록 기본 개념부터 차근차근 설명한다. 생소한 용어와 약어는 처음 등장할 때 쉬운 말로 풀어 쓴다.
- 개념과 절차는 작은 단계로 나누고, 필요한 사전 지식이나 실행 환경을 먼저 밝힌다. 독자가 앞선 단계를 완료했는지 확인할 수 있도록 실행 결과나 확인 방법을 제시한다.
- 예제 코드는 개념을 설명하는 데 도움이 되는 범위에서 가능한 한 충분히 제공한다. 짧은 코드 조각만으로 이해하기 어려운 경우 전체 실행 흐름이 보이는 예제를 우선한다.
- 예제에는 필요한 import, 설정, 실행 방법과 기대 결과를 포함한다. 생략한 부분이나 자리표시자는 명확히 표시하고 완성된 실행 예제로 오해되지 않게 한다.
- 예제 수를 늘리기 위해 중복되거나 실제 학습에 도움이 되지 않는 코드를 반복하지 않는다. 모든 예제는 현재 공개 API와 호환되고 복사해 실행할 수 있는지 확인한다.
- 기초 사용법에서 시작해 선택 설정과 고급 운영으로 이어지도록 주제와 설명 순서를 구성한다.
- 요청 처리 흐름, 작업 생명주기, 구성 요소 관계처럼 시각화가 이해에 도움이 되는 주제에는 Mermaid 다이어그램을 적극적으로 활용한다. 문서 주제에 맞는 흐름도, 시퀀스 다이어그램, 상태도 또는 구성도 등을 선택하고, 필요한 곳에는 다이어그램을 충분히 제공한다.
- Mermaid는 `mermaid` 코드 펜스로 작성한다. 노드 이름과 화살표의 방향·관계는 실제 동작과 일치시킨다.
- 다이어그램만으로 중요한 절차나 계약을 설명하지 않는다. 초보자가 그림을 읽을 수 있도록 앞뒤 문장에서 의미와 핵심 흐름을 설명한다.
- 한국어·영어 문서에 같은 다이어그램을 제공할 때 노드 문구는 해당 문서 언어로 작성하되 구조와 의미는 일치시킨다.
- 이해에 도움이 되지 않는 장식용 다이어그램은 추가하지 않고, 복잡해진 다이어그램은 이해 가능한 단위로 나눈다.

## 기술 내용의 정확성

- 내용은 DefStream의 공개 API, 구현된 동작과 지원되는 설정에 근거한다.
- 작업 정의, 구독·ACK·실패 처리, 실행 풀과 종료, 생명주기 훅, 요청·응답 계약, Inspector, 로깅, RabbitMQ 및 Redis Streams 안내는 해당 기능의 실제 계약을 확인해 작성한다.
- 설정 예시와 코드 샘플은 현재 API와 호환되어야 한다. 외부 브로커나 서비스가 필요한 절차에는 요구 사항과 실행 조건을 설명한다.
- 지원 여부가 확인되지 않은 기능, 보장되지 않는 동작, 실제 수행하지 않은 검증을 사실처럼 작성하지 않는다.
- 사용자에게 필요한 제약, 오류 동작, 호환성 또는 운영상 주의사항을 해당 주제에서 설명한다.

## 작업 완료 시 매뉴얼 갱신

- 모든 작업을 마치고 이슈별 변경 로그를 작성하기 전, 변경된 기능·사용법·설정·제약을 상세 매뉴얼에 반영해야 하는지 반드시 검토한다.
- 사용자에게 영향을 주는 공개 기능, 동작, API, 설정, 설치·운영 절차, 오류 또는 제약이 바뀌면 관련 `docs/` 상세 매뉴얼을 같은 작업에서 갱신한다. 새 동작에 맞는 예제와 Mermaid 다이어그램도 필요한지 확인한다.
- 한국어 매뉴얼을 갱신하면 대응하는 `.en.md` 영어판도 함께 갱신한다. 변경 로그 작성만으로 매뉴얼 갱신을 대신하지 않는다.
- 기존 매뉴얼에 관련 내용이 없으면 필요한 주제별 문서를 만들고, 한국어·영어 진입 문서 양쪽에서 연결한다.
- 문서 영향이 없는 내부 변경은 매뉴얼 내용을 억지로 추가하지 않는다. 완료 전 영향 검토를 수행하고, 문서 변경이 불필요한 이유를 작업 기록에 남긴다.
- 변경 로그를 작성한 뒤 변경 로그에 적은 사용자 영향과 상세 매뉴얼이 일치하는지 최종 확인한다.

## 문서 구성과 유지보수

- 제목은 문서의 주제를 명확히 나타내고, 한 문서는 하나의 주요 주제를 다룬다.
- 같은 상세 설명을 여러 문서에 복제하지 않는다. 기준 문서에 내용을 두고 다른 곳에서는 상대 링크로 연결한다.
- `README.md` 및 `README.en.md`에는 상세 설명을 복제하지 않고 `docs/README.md`로 안내한다. 공개 API나 사용법에 영향이 있는 변경이면 관련 루트 README 요약도 함께 검토한다.
- 예제에는 필요한 전제 조건을 표시하고 비밀값이나 실제 자격 증명을 넣지 않는다.
- 한국어·영어 매뉴얼을 함께 갱신해 기능, 예제 및 제약 설명이 어긋나지 않게 한다.
- 공통 마크다운 작성 지침을 따르며, 내부 링크와 앵커가 실제 문서 구조에 맞는지 확인한다.
