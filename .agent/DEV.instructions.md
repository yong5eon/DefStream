# 역할과 전문성

- 객체 지향 프로그래밍(Object-Oriented Programming)과 객체 지향 설계(Object-Oriented Design)를 고려해 개발한다.

# 개발 원칙

## SRP (Single Responsibility Principle)

- 클래스, 함수, 모듈은 하나의 명확한 책임을 갖도록 설계한다.
- 서로 다른 이유로 변경되는 역할이나 관심사가 섞여 있다면 분리를 검토한다.
- 책임 분리는 이해와 변경을 쉽게 할 때 적용하고, 불필요한 추상화로 이어지지 않게 한다.

## YAGNI (You Aren't Gonna Need It)

- 현재 명시된 요구사항과 필요한 동작만 구현한다.
- 미래에 필요할 것이라는 추측만으로 기능, 설정, 매개변수, 인터페이스, 추상화를 추가하지 않는다.
- 기존 동작이나 계약을 변경해야 한다면 영향 범위를 확인하고 필요한 변경만 수행한다.

## KISS (Keep It Simple)

- 문제의 원인과 요구사항을 직접 해결하는 가장 명확하고 단순한 방법을 선택한다. 단순함은 코드 줄 수나 당장의 변경량만으로 판단하지 않으며, 문제를 회피하거나 증상만 숨기는 우회책을 단순한 해결로 취급하지 않는다.
- 제약 때문에 우회가 불가피하거나 명시적인 요구로 우회해야 한다면, 이유와 남는 영향·한계를 확인하고 드러낸다.
- 복잡한 추상화나 디자인 패턴은 실제로 문제를 단순화하는 경우에만 사용한다.
- 중복을 제거하는 것보다 이해하기 쉬운 코드가 중요하다면 명확한 중복을 허용한다.
- 함수 길이, 조건문 중첩, 매개변수 수 등은 절대 기준으로 제한하지 않는다. 복잡성이 이해와 변경을 어렵게 만드는지 판단하는 참고 신호로 사용한다.

## 적용 기준

- 세 원칙을 기계적인 순서나 절대 규칙으로 적용하지 않는다. 요구사항, 기존 코드의 계약, 가독성과 변경 용이성을 함께 고려한다.
- 요청 범위와 무관한 리팩터링은 피한다. 기능 변경과 구조 변경을 분리하는 것이 검증과 리뷰에 도움이 될 때 작은 단위로 수행한다.
- 작업 후에는 변경에 적합한 테스트나 검증을 실행하고 결과를 확인한다.

# 공통 코드 작성 규칙

- 언어별 명명 규칙, 포맷, 관용 패턴은 해당 언어의 세부 지침과 저장소의 기존 관례를 따른다.
- 주석, 문서, 개발 과정에서 사용자에게 제공하는 설명은 한국어로 작성한다. 코드 식별자와 외부 API·라이브러리의 고유 명칭은 번역하지 않고 원문과 해당 언어의 관례를 따른다.
- 새 클래스나 상속 관계를 다룰 때는 부모 클래스 또는 인터페이스의 계약과 시그니처를 확인한다. 외부 API나 타입이 불명확한 호출도 사용 전에 계약을 확인한다.
- 예상치 못한 오류를 조용히 무시하거나 성공한 것처럼 처리하지 않는다. 오류를 적절한 맥락과 함께 전파하거나 예외를 발생시킨다.
- 폴백, 기본값, 더미 데이터는 명시된 요구사항이 있을 때만 사용한다. 오류를 숨기기 위한 대체 동작으로 사용하지 않는다.
- TODO는 지금 처리하지 않을 구체적인 작업이 남아 있을 때만 남기는 것을 권장한다. 가능한 경우 후속 작업을 식별할 수 있도록 내용을 구체적으로 작성한다.
- 요구사항이나 기존 계약과 지침이 충돌하면 임의로 계약을 깨지 않는다. 충돌과 영향 범위를 확인하고, 해결이 불명확하면 사용자에게 알린다.
