# RabbitMQ 추가 INFO 축소 대상 조사

[연결 로그 DEBUG 조정](../implements/1793257519898.md) 이후 RabbitMQ에 한정하여 더 줄일 INFO가 있는지 조사했습니다. 제품 코드는 변경하지 않았습니다.

## DefStream RabbitMQ 구현

`src/Broker/Implements/RabbitMQ/`의 로그 호출을 레벨별로 검색했습니다. 남은 INFO는 `Consumer.py`의 생명주기 로그 8곳뿐입니다.

| 위치 | 메시지 | 발생 시점 |
| --- | --- | --- |
| `Consumer.subs()` | `Subscription applied` | 등록한 Run마다 1건 |
| `Consumer.run()` | `Starting consumption loop`, `Consumption loop ended` | 소비 루프 시작·종료 |
| `Consumer.stop()` | `Consumption loop stop requested`, `Consumption loop stopped` | 중지 요청 |
| `Consumer.close()` | `RPC response channel closed`, `Consumption channel closed` | 채널 종료 |

`src/Worker/Worker.py`는 Worker 시작 시 Consumer를 한 번 생성하고 종료 시 한 번 닫습니다. 따라서 Worker 하나의 수명 동안 위 INFO는 등록한 Run 수 + 최대 6건만 남고 메시지·작업 수에 비례하지 않습니다. 사용자 제공 표본에도 나타나지 않았으므로 축소 근거가 없어 유지합니다.

WARNING은 RPC 시간 초과·원격 오류·응답 라우팅 실패, Stream 처리 예외 후 재전달 시도에서만 발생합니다. ERROR는 I/O·코덱 실패 경로입니다. 둘 다 정상 처리 경로에서는 발생하지 않으므로 이번 범위의 축소 대상이 아닙니다. 메시지 발행·수신·정산·RPC의 정상 로그는 이미 DEBUG입니다.

## pika 라이브러리 로그

DefStream은 `pika` 로거의 레벨을 설정하지 않습니다. 설치된 pika 1.4.4 소스에서 정상 경로의 INFO 호출을 확인했습니다.

- 연결: `Pika version ... connecting to ...`, `Socket connected`, `Streaming transport linked up`, `AMQPConnector - reporting success`, `AMQPConnectionWorkflow - reporting success`, `Connection workflow succeeded`
- 채널 생성: `Created channel=...`
- 종료: `Closing connection`(BlockingConnection과 Connection에서 각 1건), `AMQP stack terminated ...`, `Deactivating transport`, `Closing transport socket and unlinking`, `User-initiated close`

소스 기준 추정으로 연결 하나를 열고 닫을 때 채널 로그를 제외하고 10건 이상의 INFO가 남습니다. 로컬 RabbitMQ 서버(`localhost:5672`)에 접속할 수 없어 실측하지 못했습니다.

제공 표본에는 pika 로그가 없으므로 해당 애플리케이션은 pika INFO를 출력하지 않는 설정으로 판단합니다. 루트 로거를 INFO로 설정한 애플리케이션에서는 이 로그가 DefStream 연결 로그보다 많아질 수 있습니다. 라이브러리가 서드파티 로거 레벨을 임의로 바꾸지 않는 관례에 따라 DefStream 코드에서 조정하지 않습니다. 필요하면 애플리케이션에서 다음처럼 설정합니다.

```python
import logging

logging.getLogger('pika').setLevel(logging.WARNING)
```

RPC(`Queue.call()`, `Exchange.call()`)는 호출마다 전용 연결을 열고 닫으므로 pika INFO를 켠 환경에서는 RPC 한 번마다 위 연결 로그가 남습니다. 연결 재사용은 로깅 범위가 아니므로 변경하지 않습니다.

## 결론

DefStream RabbitMQ 구현에는 추가로 줄일 근거가 있는 INFO가 없습니다. 남은 축소 수단은 애플리케이션의 pika 로거 설정과, 작업마다 연결을 여는 사용 방식의 개선입니다. 둘 다 이번 이슈의 코드 변경 범위 밖입니다.
