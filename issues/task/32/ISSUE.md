# 모든 대상 브랜치의 PR에서 CI 검증을 실행하고 릴리즈 작업을 master push로 제한

- 이슈: [#32](https://github.com/yong5eon/DefStream/issues/32)
- 대상: [CI 워크플로](../../../.github/workflows/ci.yml)
- 참고: [DefEssential의 동일 목적 작업](../../../../DefEssential/issues/task/8/IMPLEMENTS.md)

## 작업 목적

PR의 대상 브랜치와 변경 파일 종류에 관계없이 CI 검증을 실행하고, 버전 산정과 공개 배포는 `master` push에서만 수행한다.

DefEssential에서 진행한 테스트·릴리즈 경로 분리와 같은 목적의 작업이다. 다만 워크플로 전체를 그대로 복사하지 않고 DefStream의 기존 패키지 검증, RabbitMQ·Redis 통합 테스트, UI 테스트 및 릴리즈 정책을 유지해야 한다.

## 현재 설정과 문제

아래 내용은 현재 워크플로 정의를 확인한 결과이며, GitHub Actions의 실제 실행 로그를 확인한 결과는 아니다.

### 1. master 이외의 브랜치를 대상으로 하는 PR은 CI가 실행되지 않음

- `pull_request.branches`가 `[master]`로 제한되어 있다.
- 이 필터는 PR의 소스 브랜치가 아니라 대상 브랜치(base branch)에 적용된다.
- 따라서 작업 브랜치 사이의 PR 등 `master` 이외의 브랜치로 보내는 PR은 테스트 대상에서 제외된다.

### 2. 변경 파일에 따라 PR 테스트가 생략됨

- `changes` job의 `Detect test-relevant changes` 단계가 특정 경로의 변경 여부를 계산한다.
- 검사 대상은 `samples/`, `src/`, `tests/`, `setup.py`, `.github/workflows/ci.yml`이다.
- `test` job은 `needs.changes.outputs.test_required == 'true'`일 때만 실행된다.
- 이에 따라 문서나 이슈 기록만 변경한 PR은 테스트가 생략되어, 모든 PR을 검증한다는 목적과 맞지 않는다.

### 3. PR 테스트가 릴리즈 준비 작업에 의존함

- PR에서도 공개 버전 계획, 변경 로그 검증, 릴리즈 노트 artifact 보관 단계가 실행된다.
- `test` job은 `changes` job에 의존하므로 릴리즈 태그 이력, 기존 릴리즈 노트, `issues/{브랜치}/README.md` 검증 등의 실패가 PR 테스트 실행을 막을 수 있다.
- 현재 `publish` job은 이미 `master` push로 제한되어 있다. 문제는 PR에서 실제 배포가 수행된다는 것이 아니라, 테스트에 불필요한 릴리즈 준비 작업까지 수행한다는 점이다.

## 기대 동작

| 이벤트 | 테스트·검증 | 릴리즈 준비·배포 |
| --- | --- | --- |
| `master` 대상 PR 생성·재개·커밋 갱신 | 실행 | 실행하지 않음 |
| `master` 이외의 브랜치 대상 PR 생성·재개·커밋 갱신 | 실행 | 실행하지 않음 |
| 문서·이슈 기록만 변경한 PR | 실행 | 실행하지 않음 |
| `master` push(PR 병합 및 직접 push 포함) | 실행 | 검증 성공 후 배포 |
| `master` 이외의 브랜치 push | push 이벤트로는 실행하지 않음 | 실행하지 않음 |

열린 PR의 소스 브랜치에 push하면 `pull_request`의 커밋 갱신 이벤트로 검증한다. 모든 브랜치의 `push` 트리거를 추가하여 같은 변경을 중복 검증하는 방식은 사용하지 않는다.

## 작업 범위

### 1. 모든 PR에서 테스트 실행

- `pull_request`의 대상 브랜치 필터를 제거한다.
- 기본 PR 이벤트인 `opened`, `synchronize`, `reopened`에서 검증되도록 한다.
- 변경 경로에 따른 테스트 생략 단계와 `test_required` 출력 및 테스트 실행 조건을 제거한다.
- `push` 트리거는 기존처럼 `master`만 대상으로 유지한다.
- PR 테스트가 릴리즈 버전 산정이나 변경 로그 수집 단계의 실행·출력에 의존하지 않도록 job 의존성과 조건을 정리한다.

### 2. 기존 검증 범위 유지

- Python 3.9~3.14 전체 매트릭스를 유지한다.
- PR과 `master` push 모두에서 기존 패키지 빌드 및 `twine check --strict` 검증을 유지한다.
- 기본 설치와 RabbitMQ·Redis 선택 의존성 설치 검증, 깨끗한 환경에 설치한 패키지의 테스트를 유지한다.
- RabbitMQ 4.1·Redis 7.4 서비스를 사용하는 통합 테스트와 Node.js 기반 UI 테스트를 유지한다.
- PR에서는 기존 Git 기반 개발 버전으로 검증용 배포물을 빌드하되, 공개 릴리즈 버전·빌드 번호를 산정하거나 릴리즈용 artifact로 보관하지 않는다.

### 3. 릴리즈 관련 작업을 master push로 제한

다음 작업은 `github.event_name == 'push'`이면서 `github.ref == 'refs/heads/master'`인 경우에만 수행한다.

- 공개 릴리즈 버전·wheel 빌드 번호 산정
- 릴리즈 변경 로그 수집·검증 및 `release-notes` artifact 보관
- 검증된 릴리즈 배포물의 `distributions` artifact 보관
- 버전 태그 기록, PyPI 업로드, GitHub Release 생성·갱신

PR에서는 릴리즈 태그나 기존 GitHub Release, 배포용 변경 로그의 유무가 테스트 실행의 전제 조건이 되어서는 안 된다. 이는 PR의 변경 로그 검증을 릴리즈 경로로 옮기는 것이며, 배포 시 필요한 변경 로그 검증 자체를 제거하는 것은 아니다.

`master` push에서는 기존 버전 증가·동일 버전 재빌드 정책, 변경 로그 수집 방식, 배포물 검증 및 재실행 정책을 유지한다. 배포는 모든 필수 검증이 성공한 뒤에만 수행한다.

### 4. 권한과 변경 범위

- PR 검증의 기본 권한은 읽기 전용으로 유지하고 배포 비밀이나 릴리즈용 쓰기 권한을 사용하지 않는다.
- PR 코드를 실행하기 위해 `pull_request_target`으로 전환하지 않는다.
- 라이브러리 기능, 지원 Python 버전, 브로커 동작, 패키지 구성 및 공개 버전 정책은 변경하지 않는다.
- [기존 릴리즈 워크플로 테스트](../../../tests/test_rabbitmq_release_workflow.py) 중 PR에서 버전 계획이나 변경 로그 검증을 수행한다고 가정하는 테스트는 새 계약에 맞게 갱신한다. `master` 릴리즈 정책에 대한 회귀 검증은 유지한다.

## 완료 기준

- [ ] PR 트리거에 대상 브랜치 제한이 없고, push 트리거는 `master`만 대상으로 한다.
- [ ] `master`와 비-master 대상 PR 모두에서 Python 3.9~3.14 전체 검증이 실행된다.
- [ ] 문서·이슈 기록만 변경한 PR에서도 변경 경로 조건으로 테스트가 생략되지 않는다.
- [ ] PR에 릴리즈용 변경 로그가 없거나 릴리즈 이력을 조회하지 않아도 테스트를 시작할 수 있다.
- [ ] PR에서도 패키지 빌드·설치, 선택 의존성 검증, 단위·통합 테스트 및 UI 테스트가 유지된다.
- [ ] PR에서는 릴리즈 버전 계획, 릴리즈 노트·배포물 artifact 보관, 태그 기록 및 공개 배포가 실행되지 않는다.
- [ ] `master` push에서는 기존 릴리즈 준비·배포가 유지되고 필수 검증 실패 시 배포하지 않는다.
- [ ] 비-master push는 push 이벤트로 워크플로를 실행하지 않으며, 열린 PR의 갱신은 PR 이벤트로 검증한다.
- [ ] PR 경로에 배포 비밀 사용이나 릴리즈용 쓰기 권한이 추가되지 않는다.
- [ ] 워크플로 YAML·이벤트 조건·job 의존성을 검증하고 관련 회귀 테스트를 통과한다.

## 검증 및 운영 참고

- 정적 검증에서는 트리거뿐 아니라 릴리즈 단계의 실행 조건, PR에서 생략되는 단계의 출력 사용 여부, `needs`로 인한 테스트 연쇄 생략 여부까지 확인한다.
- 실제 GitHub Actions에서는 비-master 대상 PR, 문서만 변경한 PR, `master` push의 실행 결과와 artifact·배포 단계의 실행 여부를 확인한다.
- 이벤트 기반 검증은 해당 이벤트에서 사용하는 워크플로 정의에 변경이 반영된 상태에서 수행하고, 필요한 fork PR 실행 승인 등 저장소 정책에 따른 대기는 테스트 생략 조건과 구분한다.
- 모든 PR에 전체 검증을 적용하므로 기존보다 CI 실행량과 서비스 컨테이너 사용량이 증가한다.
- 실제 실행하지 않은 검증은 완료로 표시하지 않고, 정적 검증과 원격 실행 결과를 구분하여 기록한다.
