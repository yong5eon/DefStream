# PR 검증 범위 확대와 릴리즈 작업 분리

## 모든 대상 브랜치의 PR 검증

기존에는 `master`를 대상으로 하는 PR에서만 CI가 시작되었으며, 문서나 이슈 기록만 변경하면 테스트가 생략될 수 있었습니다. 이제 대상 브랜치와 변경 파일 종류에 관계없이 PR 생성·커밋 갱신·재개 시 전체 검증을 실행하도록 CI 설정을 변경했습니다.

Python 3.9~3.14, 패키지 빌드·설치, RabbitMQ·Redis 통합 테스트와 UI 테스트의 검증 범위는 유지됩니다. 검증 대상 확대에 따라 CI 실행량과 서비스 컨테이너 사용량은 증가합니다.

## PR 검증과 공개 배포 분리

PR에서는 검증용 패키지만 빌드하고, 공개 버전 산정·릴리즈 노트 수집·릴리즈용 artifact 보관·태그 기록·공개 배포는 수행하지 않습니다. 배포용 변경 로그가 없다는 이유로 PR 테스트 시작이 차단되지 않습니다.

`master` push에서는 기존처럼 릴리즈 준비와 필수 검증이 성공한 뒤 배포합니다. 신규 릴리즈에 필요한 변경 로그 검증과 기존 버전·재빌드 정책은 유지되므로, 병합할 브랜치의 릴리즈 변경 로그 작성은 계속 필요합니다.

비-master 브랜치의 push 자체로는 CI가 실행되지 않습니다. 열린 PR이 있으면 해당 PR의 커밋 갱신 이벤트로 검증합니다.

라이브러리 사용법이나 공개 API의 변경은 없습니다. 새 실행 정책은 해당 이벤트에서 변경된 워크플로 정의를 사용하게 된 이후 적용되며, fork PR에 필요한 실행 승인 등 저장소 정책은 그대로 적용됩니다.

상세 범위는 [요구사항](./REQUIREMENTS.md), 구현 및 검증 상태는 [구현 기록](./IMPLEMENTS.md)에서 확인할 수 있습니다.
