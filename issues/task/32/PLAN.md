# 모든 PR 검증 및 master 전용 릴리즈 작업 계획

## 1. 목적과 기준

- 근거: [이슈 기록](./ISSUE.md), [요구사항 명세서](./REQUIREMENTS.md)
- 작업 브랜치: `task/32`
- 구현 대상: [CI 워크플로](../../../.github/workflows/ci.yml), [관련 회귀 테스트](../../../tests/test_rabbitmq_release_workflow.py)

DefEssential과 동일한 이벤트별 실행 정책을 적용하되, DefStream의 기존 검증 범위와 릴리즈 정책을 유지한다.

이 문서는 앞으로 수행할 구현·검증 순서를 정의한다. 계획서 작성 시점에는 CI와 테스트를 변경하지 않았으며, 아래 작업을 완료한 것으로 간주하지 않는다.

## 2. 구현 방향

### 2.1. 이벤트와 테스트 경로

- `pull_request`의 대상 브랜치 필터를 제거하고 기본 활동 유형을 유지한다.
- `push`는 `master`만 대상으로 유지한다.
- 변경 경로 검사 단계, `test_required` 출력 및 테스트 job의 해당 조건을 제거한다.
- Python 전체 매트릭스와 패키지·선택 의존성·브로커 통합·UI 검증은 변경하지 않는다.

### 2.2. 최소 변경으로 릴리즈 경로 분리

- 기존 `changes` job을 유지하고, 버전 계획·변경 로그 수집·릴리즈 노트 업로드 단계에 `master` push 조건을 적용하는 방식을 우선한다.
- `changes` job 전체를 PR에서 생략하지 않는다. 테스트의 기존 `needs: changes`를 유지하더라도 릴리즈 단계 생략 때문에 테스트가 연쇄 생략되지 않도록 한다.
- PR에서 불필요해지는 버전 계획·변경 로그 스크립트 내부 분기는 정리하되, `master` 동작과 오류 처리를 보존한다.
- PR의 릴리즈 출력값이 비어 있어도 기존 검증용 빌드 경로를 선택하도록 확인한다. 공개 버전을 임의로 채우지 않는다.
- 릴리즈용 배포물 업로드는 `master` push와 Python `3.13` 조건을 모두 만족할 때만 허용한다.
- `publish`의 이벤트·ref·릴리즈 여부 조건과 `changes`, `test` 의존성을 유지하여 필수 검증 성공 후에만 배포한다.
- 별도 공통 워크플로, 새 설정 또는 불필요한 job 분할은 추가하지 않는다.

## 3. 수행 순서

### 1단계. 구현 전 계약과 기준 상태 확인

관련 요구사항: CI-01~CI-06, SEC-01 / 인수 기준: AC-01~AC-12

1. 작업 브랜치와 기존 변경을 확인하고 사용자 변경을 보존한다.
2. Python 테스트를 수정하기 전에 [Python 개발 지침](../../../../Instructions/개발.파이썬.instructions.md)을 확인한다.
3. 워크플로의 전체 릴리즈 경로와 테스트 코드의 스크립트 추출·mock 방식을 읽는다.
4. 단계 이름, output ID, 환경변수 및 artifact 이름을 사용하는 지점을 확인한다.
5. 관련 회귀 테스트를 먼저 실행하여 기준 상태를 확인한다. 실패하면 이번 변경과 관련된 실패인지 구분한다.

완료 조건: 기존 동작을 유지할 지점과 변경할 PR 가정을 식별하고, 기준 테스트 결과를 확보한다.

### 2단계. 트리거와 테스트 실행 조건 변경

관련 요구사항: CI-01, CI-02, CI-04 / 인수 기준: AC-01~AC-05, AC-07

1. PR 대상 브랜치 제한을 제거한다.
2. `master` push 제한과 기본 PR 활동 유형을 유지한다.
3. 경로 검사 단계와 `test_required` 출력·참조를 함께 제거한다.
4. 테스트 job의 매트릭스, 서비스, 환경변수와 기존 검증 단계를 보존한다.

완료 조건: PR의 대상 브랜치나 변경 경로로 테스트를 생략하는 설정이 없고, 비-master push를 새로 활성화하지 않는다.

### 3단계. 릴리즈 준비·배포 조건 정리

관련 요구사항: CI-03, CI-05, CI-06, SEC-01 / 인수 기준: AC-06, AC-08~AC-11

1. 버전 계획, 릴리즈 변경 로그 수집·검증, 릴리즈 노트 업로드를 `master` push 전용으로 제한한다.
2. 릴리즈 스크립트에서 PR 전용 처리를 제거하고 `master` 직접 push·PR 병합·동일 버전 재빌드 처리를 유지한다.
3. PR에서 릴리즈 단계의 output이 비어 있을 때 검증용 개발 버전 빌드가 선택되는지 확인한다.
4. 릴리즈용 `distributions` 업로드 조건을 명시적으로 점검하고 Python `3.13` 산출물 사용을 유지한다.
5. 배포 job의 선행 검증과 실행 조건을 점검한다. 실패·취소·생략 시 실행을 강제하는 조건을 추가하지 않는다.
6. 기본 읽기 권한, PR checkout의 자격 증명 비보관 및 배포 환경·쓰기 권한의 범위를 확인한다.

완료 조건: PR은 릴리즈 준비 없이 검증되고, 릴리즈 산출물·공개 배포 경로는 `master` push에만 존재한다.

### 4단계. 관련 회귀 테스트 갱신

관련 요구사항: CI-01~CI-06, SEC-01 / 인수 기준: AC-01, AC-03, AC-04, AC-06~AC-12

1. PR에서도 버전 계획 스크립트가 실행된다는 기존 테스트 가정을 새 실행 조건 검증으로 대체한다.
2. PR에서 배포용 변경 로그를 요구하는 기존 테스트를 갱신하되, `master` 릴리즈에서 필요한 변경 로그 누락·빈 내용의 오류 검증은 유지하거나 보완한다.
3. 단계 이름이나 환경변수가 바뀌면 스크립트 추출 helper와 관련 mock을 함께 수정한다.
4. 트리거, 테스트 생략 조건 제거, 릴리즈 단계별 조건, 배포 job 의존성 및 PR 검증용 빌드 분기를 검증한다.
5. 신규 버전, 동일 버전 재빌드, 이전 실패 push의 변경 포함, 태그 유지, 릴리즈 노트 재사용 및 배포물 검증 관련 기존 테스트를 유지한다.
6. 기존 테스트 도구와 패턴을 우선 사용한다. 워크플로 조건 검사만을 위해 새 런타임 의존성을 추가하지 않는다.

완료 조건: PR 계약 변경과 `master` 릴리즈 동작 보존을 모두 검증하며, 제거된 PR 가정을 다른 동작의 검증 없이 단순 삭제하지 않는다.

### 5단계. 로컬 검증과 변경 검토

관련 요구사항: CI-01~CI-06, SEC-01, OPS-01 / 인수 기준: AC-01~AC-12의 로컬 검증 범위

1. 기존 환경에서 워크플로 YAML을 파싱하고, 사용 가능한 기존 워크플로 검사 도구가 있으면 함께 실행한다. YAML의 `on` 키를 올바르게 해석하는지 확인한다.
2. 워크플로 내 Python 스크립트의 구문 검증을 포함한 관련 회귀 테스트를 실행한다.
3. 이벤트 조건과 job·step 의존성을 검토하여 PR의 릴리즈 단계 생략과 테스트 실행이 양립하는지 확인한다.
4. 변경 전후의 매트릭스·서비스·검증 단계·배포 정책을 비교한다.
5. 공백 오류와 변경 범위를 확인한다. 관련 실패가 드러난 경우에만 추가 테스트로 범위를 확대한다.

관련 테스트는 프로젝트 루트에서 다음 명령으로 묶어 실행한다.

```powershell
python -m unittest discover -s tests -p test_rabbitmq_release_workflow.py -v
git diff --check
```

로컬 스크립트·조건 검증이 GitHub Actions의 이벤트 처리나 서비스 통합 테스트 전체 실행을 대신하지는 않는다.

완료 조건: 관련 회귀 테스트와 정적 검증이 통과하고, 미실행 원격 검증을 명확히 구분한다.

### 6단계. 실제 이벤트 검증

관련 요구사항: OPS-01 / 인수 기준: AC-02~AC-11의 원격 검증 범위

워크플로 반영 상태와 저장소 권한이 준비된 후 아래 항목을 확인한다.

| 시나리오 | 확인할 결과 |
| --- | --- |
| `master` 대상 PR | 전체 매트릭스와 기존 검증 실행, 릴리즈 준비·배포 미실행 |
| 비-master 대상 PR | 대상 브랜치 제한 없이 동일 검증 실행 |
| 문서·이슈 기록만 변경한 PR | 테스트 job이 변경 경로로 생략되지 않음 |
| PR 생성·커밋 갱신·재개 | 각 기본 활동 유형에서 검증 실행 |
| 배포용 변경 로그가 없는 PR | 릴리즈 준비로 인해 테스트 시작이 차단되지 않음 |
| 열린 PR의 비-master 소스 브랜치 push | PR 이벤트 검증만 생성되고 별도 push 실행은 없음 |
| PR이 없는 비-master 브랜치 push | push 이벤트 실행 없음 |
| `master` push | 릴리즈 준비와 전체 검증, 성공 후 기존 배포 경로 실행 |
| 필수 검증 실패·취소·생략 | 공개 배포가 차단됨 |

- PR 실행에서 `release-notes`, `distributions` artifact와 공개 배포가 발생하지 않는지 확인한다.
- 서비스 컨테이너와 전체 Python 매트릭스, 선택 의존성 설치 및 UI 테스트 결과를 확인한다.
- fork 승인 대기와 워크플로 조건에 따른 생략을 구분한다.
- `master` push와 공개 배포는 기존 승인·배포 절차에서 검증한다. 확인만을 위해 임의 push, 공개 버전 발행 또는 실패 유발 변경을 하지 않는다.
- 원격 실행 권한이나 반영 시점이 준비되지 않았으면 해당 항목을 미검증으로 남긴다.

완료 조건: 가능한 실제 실행 결과를 기록하고, 운영 절차에 따라 나중에 확인해야 할 항목을 별도로 남긴다.

### 7단계. 결과 기록과 변경 로그 작성

관련 요구사항: OPS-01

- 구현 후 `IMPLEMENTS.md`에 요구사항별 변경, 영향 범위와 실제 검증 결과를 기록한다.
- 별도 조사·운영 확인을 수행하면 `TASK.md`에 수행 내용과 결과를 기록한다.
- 브랜치 변경 로그인 `README.md`에는 모든 대상 PR의 검증 확대, PR에서 릴리즈용 변경 로그가 더 이상 테스트 전제 조건이 아닌 점, CI 실행량 증가 등 사용자·운영자에게 실제 반영되는 변화를 작성한다.
- 구현하지 않은 항목과 원격 미검증 항목을 완료로 기록하지 않는다.
- 구현 중 요구사항이나 순서가 달라지면 요구사항 명세서와 계획서를 함께 갱신한다.

완료 조건: 실제 변경과 검증 결과가 기록되고, 계획·구현·운영 확인 상태가 구분된다.

## 4. 주요 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 릴리즈 job 전체를 생략하여 PR 테스트까지 생략됨 | 릴리즈 step만 제한하는 최소 변경을 우선하고 `needs`와 실행 조건을 함께 검증 |
| PR의 비어 있는 output을 공개 버전으로 처리함 | PR 검증용 빌드 분기를 검증하고 임의 기본 버전을 추가하지 않음 |
| 릴리즈 스크립트 정리 중 master 정책이 달라짐 | 기존 버전·재빌드·노트·업로드 회귀 테스트 유지 |
| PR에서 artifact나 배포 권한이 노출됨 | 릴리즈 단계별 이벤트·ref 조건과 권한·환경 범위를 확인 |
| 모든 PR 검증으로 실행량 증가 | 요구사항에 따른 의도된 변화로 기록하고 검증 범위를 축소하지 않음 |
| 로컬 검사만으로 원격 동작까지 완료로 판단함 | 인수 기준별 로컬·원격 근거와 미검증 항목을 분리 기록 |

- [ ] 기존 Python·패키지·브로커 통합·UI 검증과 릴리즈 정책이 유지된다.

- [ ] 인수 기준 AC-01~AC-12 각각의 검증 근거 또는 미검증 사유가 기록된다.
- [ ] 원격 확인이 남았다면 구현·로컬 검증 완료와 운영 검증 대기 상태를 구분한다. 인수 검증 전체 완료로 표시하지 않는다.
- [ ] 실제 구현·검증 결과와 사용자·운영자용 변경 로그가 작성된다.
