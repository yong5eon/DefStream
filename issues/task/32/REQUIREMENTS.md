# 모든 PR 검증 및 master 전용 릴리즈 요구사항 명세서

## 1. 목적과 근거

- 근거 이슈: [#32](https://github.com/yong5eon/DefStream/issues/32), [로컬 이슈 기록](./ISSUE.md)
- 작업 브랜치: `task/32`
- 참고: [DefEssential의 동일 목적 요구사항](../../../../DefEssential/issues/task/8/REQUIREMENTS.md)

DefStream의 모든 대상 브랜치 PR에서 변경 파일 종류에 관계없이 CI 검증을 실행하고, 릴리즈 준비와 공개 배포는 `master` push로 제한한다.

DefEssential과 동일하게 맞추는 대상은 이벤트별 실행 정책과 테스트·릴리즈의 분리 원칙이다. 워크플로 전체를 동일하게 복사하거나 프로젝트별 검증 내용과 릴리즈 정책을 통합하는 작업은 아니다.

이 문서는 구현 전에 충족해야 할 요구사항을 정의한다. 아래 항목은 구현 또는 검증이 완료되었다는 의미가 아니다.

## 2. 범위

### 2.1. 변경 대상

- [CI 워크플로](../../../.github/workflows/ci.yml)의 이벤트 트리거, job 의존성, 테스트 실행 조건 및 릴리즈 단계 실행 조건
- [공통 릴리즈 워크플로 회귀 테스트](../../../tests/test_release_workflow.py), [RabbitMQ 관련 회귀 테스트](../../../tests/test_rabbitmq_release_workflow.py), [Redis 관련 회귀 테스트](../../../tests/test_redis_release_workflow.py)의 변경된 PR 동작에 대한 기대값과 관련 검증

### 2.2. 유지 대상 및 범위 제외

- 라이브러리의 공개 API, 브로커 동작 및 패키지 구성은 변경하지 않는다.
- Python 지원 범위와 기존 CI의 테스트·설치 검증 범위를 축소하지 않는다.
- 버전 증가, 동일 공개 버전 재빌드, 태그 처리 및 공개 배포 정책을 변경하지 않는다.
- 모든 브랜치 push, 수동 실행, 별도 이벤트 트리거를 새로 추가하지 않는다.
- 저장소의 fork 실행 승인, 브랜치 보호 및 필수 상태 검사 설정 변경은 포함하지 않는다.

## 3. 이벤트별 실행 계약

| 이벤트 또는 조건 | CI 검증 | 릴리즈 준비 | 공개 배포 |
| --- | --- | --- | --- |
| `master` 대상 PR의 생성·커밋 갱신·재개 | 실행 | 미실행 | 미실행 |
| 비-master 대상 PR의 생성·커밋 갱신·재개 | 실행 | 미실행 | 미실행 |
| 문서·이슈 기록만 변경한 PR | 실행 | 미실행 | 미실행 |
| `master` push(PR 병합 또는 직접 push) | 실행 | 실행 | 릴리즈 준비와 모든 필수 검증 성공 후 실행 |
| 비-master 브랜치 push | push 이벤트로는 미실행 | 미실행 | 미실행 |

열린 PR의 소스 브랜치에 push한 경우에는 `pull_request`의 `synchronize` 이벤트로 검증한다. 비-master 브랜치 push를 별도로 활성화하여 동일 변경에 push와 PR 검증을 중복 실행하지 않는다.

## 4. 기능 요구사항

### CI-01. 모든 대상 브랜치의 PR 검증

- `pull_request`에 대상 브랜치(base branch)를 제한하는 필터를 두지 않는다.
- 기본 활동 유형인 `opened`, `synchronize`, `reopened`를 검증 대상으로 유지한다.
- PR의 변경 경로나 파일 종류를 근거로 워크플로 또는 테스트 job을 생략하지 않는다.
- 기존 변경 경로 검사 단계, `test_required` 출력 및 이에 의존하는 테스트 실행 조건을 제거한다.
- 문서나 이슈 기록만 변경한 PR에도 일반 코드 변경 PR과 동일한 검증 범위를 적용한다.

### CI-02. master push 검증

- `push` 트리거는 `master` 브랜치로 제한한다.
- PR 병합과 직접 push를 구분하지 않고 `master` push에서 기존 CI 검증을 수행한다.
- 비-master 브랜치 push나 태그 push를 새로운 실행 대상으로 추가하지 않는다.

### CI-03. PR 검증과 릴리즈 준비의 의존성 분리

- PR에서는 공개 버전·릴리즈 빌드 번호 계획, 릴리즈 변경 로그 수집·검증, 기존 GitHub Release 조회 및 릴리즈 노트 보관을 수행하지 않는다.
- 릴리즈 준비 단계가 PR에서 생략되어도 테스트 job이 `needs` 또는 `if` 조건 때문에 연쇄적으로 생략되지 않아야 한다.
- PR에서 설정되지 않는 릴리즈 출력값을 필수 입력으로 요구하거나 유효한 공개 버전처럼 처리하지 않는다.
- PR에 릴리즈용 변경 로그가 없거나 공개 릴리즈 이력을 조회할 수 없다는 이유로 테스트 시작을 차단하지 않는다.
- 검증용 패키지 버전 산출에 필요한 기존 Git 태그 사용과 공개 릴리즈 버전 계획을 구분한다. Git 기반 개발 버전 산출 방식은 유지한다.

### CI-04. 기존 검증 범위 유지

PR과 `master` push에서 아래 검증을 유지한다.

- Python `3.9`, `3.10`, `3.11`, `3.12`, `3.13`, `3.14` 전체 매트릭스
- 기존 이벤트·빌드 유형에 따른 패키지 빌드와 `twine check --strict`
- 기본 패키지 및 `RabbitMQ`, `Redis` 선택 의존성의 독립 설치·import·의존성 검증
- 깨끗한 가상환경에 빌드된 패키지를 설치한 후 수행하는 전체 Python 테스트
- RabbitMQ `4.1`, Redis `7.4` 서비스 컨테이너와 통합 테스트 활성화 설정
- Node.js `22` 기반 기존 UI 테스트

테스트 실패를 무시하거나 실패한 검증을 성공으로 대체하지 않는다. 특정 Python 버전이나 통합 테스트를 제외하여 실행량 증가를 상쇄하지 않는다.

### CI-05. PR의 검증용 패키지 빌드

- PR에서도 기존 Git 기반 개발 버전으로 source distribution과 wheel을 빌드하고 설치·검증한다.
- 검증용 빌드에 공개 릴리즈 버전이나 릴리즈 wheel 빌드 번호를 새로 부여하지 않는다.
- 생성한 배포물은 검증에만 사용하며, 릴리즈용 `distributions` artifact로 업로드하거나 공개 배포에 사용하지 않는다.
- PR 검증을 위해 릴리즈 노트 artifact를 생성하거나 요구하지 않는다.

### CI-06. master push 전용 릴리즈 준비·배포

다음 작업은 `github.event_name == 'push'`이면서 `github.ref == 'refs/heads/master'`인 경우에만 수행한다.

| 구분 | 제한 대상 작업 |
| --- | --- |
| 버전 계획 | 공개 버전, wheel 빌드 번호, 신규 버전 여부 및 릴리즈 태그 산정 |
| 릴리즈 노트 | 변경 로그 수집·검증, 기존 릴리즈 노트 조회·재사용, `release-notes` artifact 업로드 |
| 배포물 보관 | 검증을 통과한 `distributions` artifact 업로드 |
| 공개 배포 | 버전 태그 기록, PyPI 업로드, GitHub Release 생성·갱신 |

- 릴리즈 배포물 보관은 기존 Python `3.13` 매트릭스의 검증된 산출물을 사용하는 방식을 유지한다.
- 공개 배포는 릴리즈 준비와 Python 전체 매트릭스를 포함한 모든 필수 검증의 성공을 전제로 한다.
- 필수 job의 실패·취소·생략을 성공으로 간주하여 배포하지 않는다.
- 기존 신규 버전 발행, 동일 공개 버전의 wheel 재빌드, 기존 릴리즈 노트 재사용 및 재실행 정책을 유지한다.
- PR 병합에 따른 변경 로그 수집과 `master` 직접 push의 커밋 기반 릴리즈 노트 생성 방식을 유지한다.
- 필수 릴리즈 정보나 배포물이 누락되면 기존 오류를 전파하고, 임의의 버전·빈 변경 로그·더미 산출물로 대체하지 않는다.

## 5. 권한 및 운영 제약

### SEC-01. PR 실행 권한

- 워크플로의 기본 `contents: read` 권한을 유지한다.
- PR 코드 실행 경로에서 배포 비밀, 릴리즈용 쓰기 권한 또는 `pypi` 배포 환경을 사용하지 않는다.
- PR 코드를 특권 컨텍스트에서 실행하는 `pull_request_target`으로 전환하지 않는다.
- 공개 배포에 필요한 권한과 환경은 `master` push 전용 배포 경로에 한정한다.

### OPS-01. 실행량과 이벤트 검증

- 전체 PR 검증 확대에 따른 CI 실행량과 서비스 컨테이너 사용량 증가를 허용한다.
- 실제 이벤트 검증은 해당 이벤트가 사용하는 워크플로 정의에 변경이 반영된 상태에서 수행한다.
- 저장소 정책에 따른 fork PR 실행 승인 대기는 워크플로 조건에 따른 테스트 생략과 구분한다.
- 로컬 정적 검증, 회귀 테스트, GitHub Actions 실제 실행 결과를 구분하여 기록한다. 실행하지 않은 원격 검증을 완료로 표시하지 않는다.

## 7. 검증 요구사항

### 7.1. 로컬에서 확인할 항목

- 워크플로 YAML 문법과 이벤트별 조건을 검증한다.
- PR 제한 필터와 변경 경로별 테스트 생략 조건이 제거되었는지 확인한다.
- job 의존성과 단계별 출력 사용을 확인하여 릴리즈 준비 생략이 PR 검증을 막지 않는지 검증한다.
- 릴리즈 관련 단계 및 job 전체가 `master` push로 제한되는지 확인한다.
- 관련 회귀 테스트를 실행하여 기존 릴리즈 정책과 변경된 PR 계약을 검증한다.

### 7.2. GitHub Actions에서 확인할 항목

- `master` 대상 PR, 비-master 대상 PR, 문서만 변경한 PR의 생성·커밋 갱신·재개 시 실행 결과
- PR 실행의 Python 매트릭스, 서비스 통합 테스트, 설치 검증 및 UI 테스트 결과
- PR 실행에서 릴리즈용 artifact와 공개 배포가 발생하지 않는지 여부
- `master` push의 전체 검증, 릴리즈 준비·배포 조건 및 실패 시 배포 차단 여부
- 비-master push의 별도 실행 부재와 열린 PR 갱신 시 PR 이벤트 실행 여부

공개 배포 검증은 기존 저장소의 배포 절차와 승인을 따른다. 검증만을 목적으로 임의의 공개 버전이나 릴리즈를 발행하지 않는다.

## 8. 확정 사항과 확인 필요 사항

### 확정 사항

- DefEssential과 이벤트별 실행 정책 및 테스트·릴리즈 분리 원칙을 동일하게 맞춘다.
- DefStream 고유의 검증과 기존 릴리즈 정책은 유지한다.
- 이번 요구사항 명세 작성에서는 CI 구현, 저장소 설정 변경 및 공개 배포를 수행하지 않는다.

### 확인 필요 사항

- 기능 범위에 관해 추가 결정을 기다리는 사항은 없다.
- 원격 실행 검증 시에는 워크플로 반영 상태와 저장소의 승인·배포 환경 정책을 확인해야 한다. 이는 실행 시 확인할 운영 조건이며, 미확인 상태를 검증 완료로 기록하지 않는다.
