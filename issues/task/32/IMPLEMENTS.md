# 모든 PR 검증 및 master 전용 릴리즈 구현 기록

## 1. 기준과 상태

- 근거: [이슈](./ISSUE.md), [요구사항](./REQUIREMENTS.md), [작업 계획](./PLAN.md)
- 작업 브랜치: `task/32`
- 상태: 구현 및 로컬 검증 완료, GitHub Actions 실제 이벤트·배포 검증 대기

DefEssential과 동일하게 이벤트별 실행 정책과 테스트·릴리즈 분리 원칙을 적용했다. DefStream 고유의 검증과 기존 공개 배포 정책은 유지했다.

## 2. 주요 변경

### CI-01·CI-02: 이벤트와 테스트 실행

[CI 워크플로](../../../.github/workflows/ci.yml)를 다음과 같이 변경했다.

- PR 대상 브랜치 필터를 제거했다. 기본 PR 활동 유형인 생성·커밋 갱신·재개를 유지한다.
- push 트리거는 `master`로 제한한 기존 설정을 유지한다.
- 변경 경로를 검사하던 단계, `test_required` 출력 및 테스트 job의 실행 조건을 제거했다.
- 문서·이슈 기록만 변경한 PR도 테스트 대상으로 포함했다.

### CI-03·CI-05: PR과 릴리즈 준비 분리

- 기존 `changes` job을 유지하고 이름을 `Prepare CI and master release metadata`로 변경했다.
- 버전 계획, 변경 로그 수집·검증, 릴리즈 노트 artifact 보관 단계에 `master` push 조건을 추가했다.
- `changes` job 전체는 PR에서 생략하지 않는다. 테스트의 `needs: changes`를 유지하면서 릴리즈 단계 생략이 테스트 job 생략으로 이어지지 않게 했다.
- 릴리즈 스크립트에서 PR 버전 계획과 PR 변경 로그 검증 분기를 제거했다.
- 사용처가 없는 변경 로그 단계의 `branch` 출력과 단계 ID를 제거했다.
- PR에서는 릴리즈 출력값이 비어 있어도 기존 검증용 개발 버전 빌드 분기가 선택된다. 이 분기는 공개 버전을 설정하거나 릴리즈 요약을 생성하지 않는다.

### CI-04·CI-06·SEC-01: 기존 검증·배포 정책 유지

- Python 3.9~3.14, RabbitMQ 4.1, Redis 7.4, Node.js 22와 기존 설치·패키지·통합·UI 검증 단계를 유지했다.
- 릴리즈용 배포물 업로드 조건에 `master` push를 명시했고, 기존 릴리즈 여부 및 Python 3.13 조건도 유지했다.
- `publish` job의 내용은 변경하지 않았다. `master` push 조건, 릴리즈 여부, `changes`·`test` 의존성, 배포 환경과 권한을 유지한다.
- 기본 읽기 권한과 PR 실행 경로의 자격 증명 비보관 설정을 유지했다. PR에 배포 비밀이나 쓰기 권한을 추가하지 않았다.

## 3. 회귀 테스트

동일 워크플로를 참조하는 다음 세 파일을 함께 갱신했다.

- [공통 회귀 테스트](../../../tests/test_release_workflow.py)
- [RabbitMQ 회귀 테스트](../../../tests/test_rabbitmq_release_workflow.py)
- [Redis 회귀 테스트](../../../tests/test_redis_release_workflow.py)

변경한 검증 내용은 다음과 같다.

- 모든 대상 PR과 `master` push만 허용하는 트리거 및 변경 경로 조건 제거
- PR에서 릴리즈 단계만 생략하고 선행 job·테스트 job은 생략하지 않는 구조
- 릴리즈 단계별 `master` push 조건, 배포물 보관 매트릭스 조건과 배포 job 의존성
- PR 검증의 권한 범위와 릴리즈 출력 없는 개발 버전 빌드
- `master` push의 릴리즈 계획
- 병합 릴리즈에서 변경 로그 누락·빈 내용 오류 및 정상 변경 로그 수집
- 직접 push와 PR 병합 후 재빌드에서 기존 릴리즈 노트 재사용

신규 버전, 동일 버전 재빌드, 이전 실패 push의 변경 포함, 태그 유지, 업로드 재실행·충돌 오류, 기존 GitHub Release 노트 보존과 source archive 재현성 검증은 유지했다.

## 5. 영향과 미검증 사항

- 모든 PR에 전체 검증을 적용하므로 CI 실행량과 서비스 컨테이너 사용량이 증가한다.
- PR에서는 배포용 변경 로그가 없어도 테스트를 시작할 수 있지만, 병합 후 신규 릴리즈 준비에 필요한 변경 로그 검증은 유지된다.
- 워크플로의 실제 이벤트 실행, artifact 보관, fork 승인 동작, PyPI 및 GitHub Release 연동은 확인하지 않았다.
- 원격 push, 검증용 PR 생성 및 공개 배포를 수행하지 않았다. 원격 검증은 워크플로 반영과 기존 승인·배포 절차에 따라 수행해야 한다.
- 따라서 구현·로컬 검증 완료와 인수 검증 전체 완료를 구분하며, 전체 인수 검증은 아직 완료되지 않았다.
