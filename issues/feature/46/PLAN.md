# Worker 내부 실행기 및 RabbitMQ 연결 복구 계획

작업 대상과 원문은 [이슈 기록](./README.md), 확정 동작과 인수 기준은 [요구사항 명세](./REQUIREMENTS.md)를 따릅니다. 아래 수행 단계에 실제 상태를 반영했습니다. 구현 설명은 [구현 종합](./IMPLEMENTS.md), 검증 결과와 환경 제한은 [최종 검증 기록](./tasks/1793275501812.md)을 참고하세요.

## 구현 기준과 선행 결정

- 별도 supervisor 없이 Worker 안에서 복구합니다. 전달받은 Pool 객체는 유지하고 내부 실행기와 브로커 연결·Consumer를 교체합니다.
- 최대 복구 시도 횟수와 고정 간격은 설정 가능하게 하고 기본값은 5회·60초로 둡니다. backoff나 메시지 재시도 기능은 추가하지 않습니다.
- 장애 난 실행 세대를 먼저 격리합니다. ProcessPool의 이전 프로세스는 종료하고, ThreadPool의 이전 작업은 기다리지 않되 완료 후 이전 실행 환경이 정리되게 합니다.
- 정상 종료와 장애 복구를 분리하고 기존 ACK·실패 정책·RPC 및 Redis 소비 계약을 유지합니다.
- 복구 지원은 `Recoverable` Protocol의 런타임 구조 검사로 구분하며 별도 지원 플래그를 사용하지 않습니다. 기본 Consumer·Redis의 비지원 및 상속 없는 구현의 구조적 지원을 검증합니다.
- Python 지원 범위는 현재 패키지의 3.9 이상을 유지합니다. 최신 Python에만 있는 프로세스 종료 API를 전제로 구현하거나 사설 executor 속성 조작을 검증 없이 채택하지 않습니다.

다음 세부 계약을 구체화해 요구사항에 반영했습니다. 사용자 확인대로 첫 시도는 즉시 수행하고 실패한 시도 사이에만 대기하며, 연결·전체 구독 복구 성공 시 다음 장애의 횟수를 초기화합니다. 공개 설정은 Worker의 `recovery_attempts`·`recovery_interval`이며, 지원 실행기와 오류 분류는 요구사항에 명시했습니다.

1. 복구 설정의 공개 위치·이름·입력 검증과 기존 생성자 호출 호환성
2. 최초 복구 시도 전 대기 여부, 복구 성공 후 후속 장애의 횟수 집계·초기화 기준
3. 브로커 종료 사유·예외의 복구 가능 분류와 사용자 작업 예외를 구분하는 경계
4. 지원 Python 범위에서의 프로세스 종료 수단, 사용자 지정 Pool·executor의 지원 계약

## 수행 단계와 진행 상태

CI 후속 수정 완료: Linux spawn 자식이 Event를 복원하기 전에 부모의 세마포어가 제거되지 않도록 프로세스별 draining Event를 보관합니다. 수정 전 실패를 Windows의 참조 수명 테스트와 Linux 실제 프로세스로 재현하고 Linux 기능 회귀·Windows 대상 테스트로 검증했습니다.

후속 리뷰 4건 보완 완료: 프로세스별 공유 완료 신호로 정상 종료 메시지 수신 경쟁을 제거하고 결과 수신 중에도 crash를 검사합니다. graceful cleanup 실패는 다른 작업 drain 이후 전파하며 Pool의 stop 요청은 restart 설치 단계에서 재확인합니다. 실제 프로세스 cleanup·제어된 큐 경계·동시 stop/restart 테스트와 구버전·전체 기능 회귀로 검증했습니다.

PR 리뷰 보완 완료: 종료 중 프로세스 장애·생존 프로세스 회수, 소비 시작 직전 stop 경쟁, 복구 가능한 정리 오류 이후 재연결, 사용자 지정 executor의 비대기 종료를 수정했습니다. 실제 프로세스 종료 및 Pika 소비 루프의 타이머 구동 테스트를 추가하고 Python 3.9·3.10과 기능 회귀로 검증했습니다. 기존 복구 정책과 ThreadPool 잔존 제한은 유지합니다. 결과와 미실행 범위는 [PR 리뷰 수정 검증](./tasks/1793277424063.md)을 참고하세요.

### 1. 세부 계약 및 기준 동작 확인

상태: 완료

- 위 선행 결정을 확정하고 R-02·R-07·R-09의 구체적인 계약을 보완합니다.
- 기존 Consumer의 종료 감지와 연결 재사용, Pool·Executor의 시작·종료·콜백, Worker의 pending·Inspector·cleanup 흐름을 대조합니다.
- 관련 기존 테스트에서 필요한 최소 기준 검증을 실행합니다. 전체 테스트를 선행 조건으로 삼지 않습니다.

### 2. Pool 객체를 유지하는 실행기 생명주기 구현

상태: 완료 / 선행: 1단계

대상: [Pool.py](../../../src/Worker/Pool.py), [Executor.py](../../../src/Worker/Executor.py)

- 정상 종료와 별도로 장애 실행 세대를 폐기하고 내부 실행기를 재구성하는 경로를 만듭니다.
- 세대마다 Future·작업 슬롯·결과 큐·monitor·manager 및 worker 상태를 독립시켜 이전 결과가 새 상태에 섞이지 않게 합니다.
- 이전 미실행 작업을 폐기합니다. ProcessPool은 기존 자식 프로세스를 종료·회수하고, ThreadPool은 새 작업 수신을 중단한 뒤 실행 중 작업 완료 후 종료되게 합니다.
- 이전 ThreadPool 결과 수집과 자원 정리를 새 실행기 상태에 의존하지 않게 합니다. 현재 사용자 Future가 이미 실행 상태로 표시되는 점을 고려해 단순 `Future.cancel()`만으로 작업 폐기를 구현하지 않습니다.
- setup·cleanup 훅의 실행 단위를 확인합니다. 강제 종료한 프로세스에서 cleanup 완료를 보장한다고 표현하지 않습니다.

대응: R-06·R-09, AC-03·AC-10·AC-11

### 3. RabbitMQ 소비 장애 감지 및 연결 교체 경로 구현

상태: 완료 / 선행: 1단계

대상: [Consumer.py](../../../src/Broker/Implements/RabbitMQ/Consumer.py), [Connection.py](../../../src/Broker/Implements/RabbitMQ/Connection.py), 필요한 경우 [Event.py](../../../src/Broker/Implements/RabbitMQ/Event.py)

- 소비 루프 대기 중에도 채널 종료를 감지하고, 정상 stop과 예상치 못한 종료를 구분합니다.
- ACK timeout의 종료 사유를 일반 연결 장애와 구분해 기록합니다. 브로커가 제공하는 큐·consumer 식별 정보와 로컬 구독 정보를 대조하고 특정할 수 없는 원인을 임의의 큐로 단정하지 않습니다.
- 연결이 열린 채 채널만 닫힌 경우에도 복구 시 기존 연결을 재사용하지 않도록 명시적으로 교체합니다. 이전 응답 채널·publisher 참조도 새 연결에 맞게 정리합니다.
- 장애를 Worker 복구 경계로 전달하고, 작업 오류·직렬화 오류 등과 구분합니다. 구독 복원은 기존 명시적 큐 선언 계약을 유지하며 큐 자동 삭제·재생성을 하지 않습니다.

대응: R-01·R-04·R-07·R-08, AC-04·AC-05

### 4. Worker 복구 순서 및 이전 콜백 격리 구현

상태: 완료 / 선행: 2·3단계

대상: [Worker.py](../../../src/Worker/Worker.py), 1단계에서 정한 복구 설정의 공개 위치

- 소비 실패 시 이전 실행 세대를 무효화하고 이전 풀 작업을 정리한 뒤 내부 실행기·연결·Consumer를 새로 구성합니다. 기존 Run의 handler·QoS·구독을 복원하고 전체 등록이 성공한 뒤 소비를 재개합니다.
- 설정된 횟수와 고정 간격으로 복구하며 대기 중 stop 요청도 처리합니다. 부분 복구 실패의 자원을 정리하고 확정된 집계 기준을 적용합니다.
- 예약된 이전 완료·실패 콜백도 실행 시점에 세대를 확인하도록 하여 정산·RPC 응답 및 새 pending·Inspector 상태 변경을 차단합니다.
- 복구 가능성이 남아 있는 장애를 Worker 최종 종료로 처리하지 않습니다. 반대로 비복구 장애·한도 초과 시에는 무한 drain 없이 실패를 전파합니다.
- 준비·복구 중·최종 종료 상태와 기존 Inspector 표시를 일치시킵니다. 정상 stop은 기존 graceful shutdown 경로를 유지합니다.

대응: R-02~R-07·R-09·R-10, AC-01~AC-03·AC-06·AC-07·AC-10·AC-11

## 전환·실패 시 처리와 완료 기준

- 큐 스키마나 운영 데이터를 변경하지 않습니다. 외부 supervisor·배포 정책 변경도 수행하지 않습니다.
- 새 설정을 생략한 기존 호출의 호환성을 유지하되, 소비 장애 시 실행기·연결 복구가 발생하는 의도된 동작 변화와 ThreadPool 제한은 매뉴얼에 명시합니다.
- 복구 중 만들어진 일부 자원도 다음 시도나 최종 실패 전에 정리합니다. 실패를 정상 동작으로 대체하거나 이전의 고장 난 실행기를 재사용하지 않습니다.
- 되돌림이 필요하면 해당 코드·설정 변경을 되돌려 기존 동작으로 복원합니다. 이미 실행된 작업의 외부 효과나 메시지 재전달을 되돌리는 데이터 복구는 제공하지 않습니다.
- 완료 시 AC-01~AC-11의 실제 충족 여부, 문서·코드 일치, 이전 세대 자원과 콜백의 잔존 영향, 미실행 검증을 확인합니다. 커밋·푸시·PR 생성은 별도 요청 없이 수행하지 않습니다.
