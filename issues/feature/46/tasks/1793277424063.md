# PR 리뷰 수정 회귀 검증

## 실행 범위와 결과

저장소 루트에서 기존 unittest 진입점을 사용했습니다. 테스트 모듈 경로는 `tests`, 출력 인코딩은 UTF-8로 지정했습니다. 외부 RabbitMQ·Redis 통합 opt-in은 비활성화했습니다.

- Python 3.12.10: `test_broker_packaging`을 제외한 `tests/test_*.py` 모듈 전체를 `python -m unittest`에 전달해 302개 실행, 287개 통과·15개 생략·실패 0건을 확인했습니다.
- Python 3.9.13·3.10.11: 각각 `python -m unittest test_worker_recovery test_lifecycle_hooks test_process_signals`에서 36개 통과했습니다. 기존 설치 경로의 작업 소스와 Pika 의존성을 공유했으며 Redis 의존성이 필요한 모듈은 이 구버전 검증에 포함하지 않았습니다.
- 대상 테스트 묶음 `test_worker_recovery test_lifecycle_hooks test_process_signals test_rabbitmq_logging`은 Python 3.12.10에서 50개 통과했습니다.
- Worker·Pool·RabbitMQ Connection·복구 테스트의 Pylance 타입 오류는 없습니다. Executor의 기존 `cancel_futures` 및 테스트 콜백의 미사용 매개변수 힌트는 남아 있습니다.
- 핵심 변경 diff와 `git diff --check`를 확인했습니다.

## 리뷰별 검증

1. 종료 중 프로세스 장애: 실제 spawn 프로세스에 종료 요청 후 `os._exit(7)`·`os._exit(0)`을 실행해 미완료 Future 실패와 monitor 종료를 확인했습니다. 정상 종료는 별도 테스트에서 오류 없이 완료됐습니다.
2. 생존 프로세스 회수: 다른 작업 프로세스가 실행 중인 상태에서 한 프로세스를 종료하고, 실패 콜백 실행 시점에 모든 작업 프로세스가 종료됐음을 확인했습니다.
3. stop 경쟁: running 공개 직전에 stop을 호출하도록 순서를 제어해 Consumer.run 미진입을 확인했습니다.
4. 정리 오류: Consumer·브로커 close의 복구 가능한 오류에도 한 번의 복구 시도에서 재연결·구독이 복원됨을 확인했습니다. 복구 불가능한 오류는 전파하며, RabbitMQ Connection.close 실패 후 이전 연결·publisher 참조를 재사용하지 않음을 확인했습니다.
5. 사용자 지정 executor: 비복구 오류·복구 비활성화에서 원래 오류가 보존되고 비대기 shutdown이 호출됐습니다. 복구를 요청하면 기존처럼 TypeError를 전달하되 종료 요청은 수행합니다.
6. 대기 중 채널 종료: 실제 Pika BlockingChannel의 소비 루프와 채널 종료 전달 코드를 사용했습니다. 가짜 I/O가 첫 타이머를 열린 채널에서 실행하고 다음 타이머에서 채널을 닫도록 하여 실제 대기 경로에서 브로커 예외가 전파됨을 확인했습니다. 타이머 등록·재등록이 없으면 이 테스트는 통과하지 못합니다.

## 제한

테스트의 가짜 I/O는 실제 RabbitMQ 서버가 아닙니다. 실제 브로커 장애 주입과 Linux CI 재실행은 수행하지 않았습니다. 패키징 환경 검사는 기존에 확인한 메타데이터 문제로 기능 회귀에서 제외했으며, 이를 통과했다고 보고하지 않습니다. 커밋·푸시·PR 댓글·상태 변경은 수행하지 않았습니다.
