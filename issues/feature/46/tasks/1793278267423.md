# 후속 PR 리뷰 4건 회귀 검증

저장소 루트에서 기존 unittest 진입점을 사용했습니다. 출력은 UTF-8, 테스트 모듈 경로는 `tests`로 지정했습니다.

- Python 3.12.10에서 패키징 모듈을 제외한 `tests/test_*.py` 전체: 305개 실행, 290개 통과·15개 생략·실패 0건
- Python 3.9.13·3.10.11의 `python -m unittest test_worker_recovery test_lifecycle_hooks test_process_signals`: 각각 39개 통과
- 구버전 검증은 기존 작업 소스·Pika 설치 경로를 공유했으며 Redis 의존 모듈을 포함한 전체 검증은 아닙니다.

새 테스트는 다음 경계를 확인합니다.

1. 실제 ProcessPool의 idle 프로세스 cleanup 오류가 발생한 뒤에도 다른 실행 중 Future는 미완료 상태를 유지하고 프로세스가 생존합니다. 작업을 해제하면 정상 결과를 받은 뒤 shutdown에서 cleanup 오류가 전파됩니다.
2. 큐 get 경계에서 완료 신호가 바뀌어도 exit code 0 정상 종료를 crash로 오인하지 않습니다.
3. timeout 없이 결과가 들어오는 경계에서도 비정상 exit code 및 완료 신호 없는 exit code 0 종료를 감지합니다.
4. 별도 restart 스레드를 실행기 폐기 직후 대기시키고 stop을 반환시킨 다음 restart를 재개합니다. Pool이 닫힌 상태와 기존 실행기 참조를 유지하고 이후 submit을 거부함을 확인했습니다.

이전 실제 프로세스 crash·생존 프로세스 회수·정상 종료·훅 테스트도 함께 통과했습니다. 외부 브로커 통합 opt-in은 비활성화했으며 실제 RabbitMQ 장애 주입·Linux CI 재실행·패키징 환경 검증은 수행하지 않았습니다.

Pylance 소스 Executor에는 기존 미사용 매개변수 힌트만 남습니다. 테스트에서는 junction으로 연결된 설치 경로의 이전 Executor 타입 분석 때문에 새 `completed` 속성에 `reportAttributeAccessIssue`가 표시됩니다. 런타임과 작업 소스 선언은 확인했으며 타입 무시나 우회 코드는 추가하지 않았습니다.
