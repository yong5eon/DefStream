# RabbitMQ Consumer 복구 및 종료 요구사항

## 목적

RabbitMQ 브로커가 소비 채널을 닫았을 때 소비가 영구 중단된 채 Worker 프로세스만 남는 상황을 방지합니다. 복구 가능한 소비 연결·채널 장애는 정해진 한도 안에서 복구하고, 복구할 수 없는 장애나 한도 초과는 숨기지 않고 실패로 드러내야 합니다.

이슈 원문과 작업 브랜치·병합 대상은 [이슈 기록](./README.md)을 기준으로 합니다. 원문의 해결 제안과 이후 사용자 확정을 구분하며, 아래 요구사항은 사용자와 합의한 Worker 내부 복구 방식을 반영합니다. API와 오류 분류는 [구체화한 구현 계약](#구체화한-구현-계약)에 정리했습니다.

## 분석과 근거

### 이슈에서 요청한 결과

- 브로커·연결 계층의 복구 가능한 장애가 발생하면 횟수 제한 안에서 소비를 재개합니다.
- `stop()`에 의한 정상 종료는 장애 복구와 구분합니다.
- 연결·채널을 복구한 뒤 QoS와 기존 구독을 다시 적용합니다.
- 채널이 닫힌 동안 전달된 이벤트의 delivery tag를 새 채널에서 정산하지 않습니다.
- 복구 한도를 넘거나 복구할 수 없는 장애는 Worker 실패로 전파하고, 작업 종료가 무기한 지연되지 않게 합니다.
- ACK timeout으로 인한 채널 종료는 일반 연결 장애와 구분해 큐와 timeout 초과 사실을 로그로 확인할 수 있게 합니다.

이슈에 적힌 RabbitMQ 3.13.7의 장애 사례와 `process_data_events()` 동작은 이슈 작성자의 실측 보고입니다. 이번 문서 작성 과정에서 실제 브로커로 재현한 결과는 아닙니다.

### 현재 코드와 요구사항의 차이

- [RabbitMQ Consumer](../../../src/Broker/Implements/RabbitMQ/Consumer.py)는 생성 시 채널과 QoS를 설정하고, `subs()` 호출 때 현재 채널에 구독을 등록합니다. `run()`은 `start_consuming()`을 실행하고 예외를 다시 던지지만, 연결 재생성이나 재구독은 하지 않습니다. `stop()`은 명시적 종료 요청으로 소비를 중지합니다.
- [Worker](../../../src/Worker/Worker.py)는 등록된 여러 `Run`을 하나의 Consumer에 구독합니다. 소비 루프가 끝나면 `finally`에서 pending delivery를 기록하고 작업 풀을 정리하므로, 공유 채널 장애가 여러 큐의 소비에 영향을 줄 수 있습니다.
- [RabbitMQ Event](../../../src/Broker/Implements/RabbitMQ/Event.py)는 전달 당시의 채널과 delivery tag를 보관하여 `ack()`, `nack()`, `reject()`에 사용합니다. 따라서 채널 교체 후 이전 이벤트의 정산을 새 채널에 보내지 않도록 세대를 구분해야 합니다.
- [Pool](../../../src/Worker/Pool.py)의 `stop()`은 `shutdown(wait=True)`를 호출합니다. [Executor](../../../src/Worker/Executor.py)도 대기 옵션이 참이면 내부 monitor와 manager의 종료를 기다립니다. 소비 실패 후 이 경로에서 실행 중인 작업을 무기한 기다릴 수 있다는 이슈의 문제 제기와 일치합니다.
- [RabbitMQ Worker 테스트](../../../tests/test_rabbitmq_worker.py)와 [Worker 테스트](../../../tests/test_worker.py)는 구독 등록·정산·Worker 동작을 검증하는 기존 회귀 테스트 위치입니다. 장애 복구, 채널 세대 분리, 실패 종료에 대한 인수 검증은 추가로 필요합니다.

### 범위 해석

- 복구 대상은 소비 연결·채널의 장애이며, 사용자 작업에서 발생한 예외를 다시 실행하는 기능은 아닙니다.
- 복구가 성공하면 기존 큐와 handler 등록을 보존하고 소비를 재개해야 합니다. 채널 복구를 이유로 큐를 삭제하거나 메시지를 수동 정산하지 않습니다.
- 채널 종료 시 브로커가 미확인 메시지를 재전달할 수 있으므로 복구 중 원래 작업과 재전달 작업이 겹칠 가능성이 있습니다. 이슈는 메시지 처리의 멱등성을 사용하는 쪽의 책임으로 둡니다. 이 기능은 exactly-once 처리나 중복 실행 방지를 약속하지 않습니다.
- 원문의 제안 이후 사용자는 별도 supervisor 없이 Worker 안에서 실행 풀과 연결을 복구하는 방향을 확정했습니다. 원문은 보존하되, 구현 방향은 아래 합의를 따릅니다.

### 사용자와 확정한 복구 방식

1. 소비 연결·채널 장애를 감지하면 이전 실행 세대의 작업과 정산 경로를 분리하고 소비를 중단합니다.
2. 사용자가 전달한 Pool 객체는 유지하면서 내부 실행기에 종료를 요청합니다. ProcessPool의 기존 작업 프로세스는 종료하고, ThreadPool의 실행 중 작업은 완료를 기다리지 않습니다.
3. Pool의 내부 실행기를 새로 구성하고, 브로커 연결부터 다시 생성한 뒤 소비 채널·QoS·기존 구독을 복원합니다. 닫힌 채널만 새로 만드는 복구에 한정하지 않습니다.
4. 복구 시도 한도와 시도 간 고정 간격을 설정할 수 있어야 하며 기본값은 각각 5회와 1분입니다. 별도 backoff나 외부 supervisor는 도입하지 않습니다.

구현 시작 전 추가 확인에 따라 첫 복구는 즉시 시도하며, 실패한 시도 사이에만 고정 간격을 적용합니다. 연결과 전체 구독 복구가 성공하면 다음 장애의 시도 횟수를 초기화합니다. 따라서 짧은 복구 성공과 장애가 반복되는 경우 Worker 전체 생애의 누적 복구 횟수를 제한하지는 않습니다.

ThreadPool의 이전 작업은 강제 종료하지 않습니다. 이전 실행기는 새 작업을 받지 않고, 이미 실행 중인 작업이 끝난 뒤 해당 스레드와 실행 환경이 정리되어야 합니다. 작업 자체가 끝나지 않으면 스레드도 남을 수 있습니다. 그동안 이전 작업과 재전달 작업의 중복 실행, 외부 부작용, 자원 점유 및 프로세스 종료 지연 가능성은 수용하는 제한입니다.

## 확정 요구사항

### 포함 범위

| ID | 요구사항 |
| --- | --- |
| R-01 | RabbitMQ 소비 중 연결·채널 장애를 감지해야 합니다. 감지는 ACK·NACK 시점의 예외에만 의존하지 않아야 하며, 소비 이벤트 루프가 대기 중인 경우에도 채널 종료를 놓치지 않아야 합니다. |
| R-02 | 복구 가능한 브로커·연결 계층 장애는 설정 가능한 최대 복구 시도 횟수 안에서만 복구해야 합니다. 기본값은 5회이며, 복구 시도 간 고정 대기 간격도 설정 가능해야 하고 기본값은 1분이어야 합니다. |
| R-03 | `Worker.stop()` 등 명시적 정상 종료는 장애 복구 시도로 처리하지 않아야 합니다. 정상 종료 시 기존 graceful shutdown 동작은 유지해야 합니다. |
| R-04 | Worker 안에서 Pool의 내부 실행기와 브로커 연결부터 복구하고, 새 소비 채널에 기존 QoS와 모든 등록 큐·handler를 다시 적용한 뒤 소비를 재개해야 합니다. 일부 구독만 복구된 상태를 성공으로 처리해서는 안 됩니다. 별도 supervisor 프로세스나 Worker 프로세스 재시작을 복구의 전제로 두지 않아야 합니다. |
| R-05 | 복구에 성공하더라도 기존 메시지의 ACK·NACK·REJECT 정책, QoS 및 RPC 응답 동작을 변경하지 않아야 합니다. 사용자 작업 오류를 소비 연결 장애로 취급하거나 작업 재시도를 추가하지 않아야 합니다. |
| R-06 | 이전 채널·실행기의 완료·실패 콜백은 이전 delivery tag로 정산하거나 새 Consumer를 통해 RPC 응답을 보내서는 안 됩니다. 폐기 시 경고를 남기고, 이전 콜백이 새 실행기의 Future·슬롯, Worker의 새 pending·Inspector 상태를 변경하지 않도록 실행 세대를 격리해야 합니다. 이전 세대의 상태도 해당 작업 완료·폐기에 맞춰 정리해야 합니다. |
| R-07 | 이슈의 `ChannelClosedByBroker`, `ConnectionClosedByBroker`, `StreamLostError` 예시를 포함해 소비 장애의 원인과 복구 가능 여부를 분류해야 합니다. 작업 코드 예외를 복구 대상으로 혼동하지 않아야 하며, 복구할 수 없는 예외와 시도 한도 초과는 조용히 무시하거나 정상 종료처럼 보이지 않게 Worker 실패로 전파해야 합니다. |
| R-08 | ACK timeout으로 채널이 닫힌 경우 일반 연결 장애와 구분 가능한 경고를 남겨야 합니다. 로그에는 확인 가능한 범위에서 원인, 관련 큐, ACK timeout 초과 사실이 포함되어야 합니다. |
| R-09 | 사용자가 전달한 Pool 객체는 유지하고 내부 실행기만 종료·재생성할 수 있어야 합니다. 장애 시 기존 실행기의 미실행 작업은 새 실행기에 이월하지 않고 폐기하며, ProcessPool의 기존 작업 프로세스는 종료해야 합니다. ThreadPool은 실행 중 작업의 완료를 기다리지 않고 복구를 진행하되, 이전 실행기에 종료를 요청하여 작업 완료 후 스레드와 관련 자원을 정리해야 합니다. 정상 종료의 기존 작업 대기 계약은 유지해야 합니다. |
| R-10 | 복구 불가 또는 한도 초과 시 이전 작업의 완료를 무기한 기다리지 않고 Worker 실행 경로에 실패를 전파해야 합니다. 소비 중단을 건강한 상태나 성공으로 보고해서는 안 됩니다. 다만 끝나지 않는 이전 ThreadPool 작업 때문에 Python 프로세스 종료가 지연될 수 있으며, 이번 범위에서는 그 프로세스의 강제 종료를 보장하지 않습니다. |
| R-11 | 새 동작의 사용자 설정·운영 방법이 확정되면 한국어·영어 RabbitMQ 매뉴얼에 해당 설정, 실패·재전달 동작과 제한사항을 반영해야 합니다. 매뉴얼 갱신 필요 여부와 대상은 구현 시 확정된 공개 계약에 맞춰 정합니다. |

### 제외 범위

- 작업 코드 예외에 대한 재시도, retry queue, 지연 재시도 및 중복 제거
- exactly-once 처리 또는 메시지 처리의 멱등성 보장
- 메시지 처리 중 ACK 연장, consumer timeout 설정 자체의 추가 또는 변경. consumer timeout 설정은 [관련 이슈 #47](https://github.com/yong5eon/DefStream/issues/47)에서 별도로 다룹니다.
- `Run`마다 연결·채널을 분리하거나 ThreadPool 작업을 별도 프로세스로 격리하는 구조 변경
- 운영 환경의 RabbitMQ 설정·큐·컨테이너 재시작 정책 변경
- 별도 supervisor, 외부 프로세스 재시작 정책 및 backoff 도입
- 실행 중인 Python 스레드 또는 Worker 프로세스의 강제 종료

## 인수 기준

| ID | 검증 기준 |
| --- | --- |
| AC-01 | 기본 설정에서 복구 시도가 최대 5회이며 시도 간 간격이 고정 60초임을 확인합니다. 사용자 지정 횟수·간격도 적용되며, 성공 시 새 연결·소비 채널에 기존 QoS와 모든 구독·handler가 복원되어 소비가 재개됩니다. |
| AC-02 | `stop()`에 의한 정상 종료는 재연결·재구독하지 않으며, 기존 graceful shutdown과 ACK·NACK·REJECT 및 RPC 회귀 테스트가 유지됩니다. |
| AC-03 | 이전 실행 세대의 성공·실패 콜백이 복구 전후 어느 시점에 발생해도 새 채널의 정산·RPC 응답 API를 호출하지 않고 새 Future·슬롯·pending·Inspector 상태를 변경하지 않습니다. 폐기 경고와 이전 세대 상태의 정리를 확인합니다. |
| AC-04 | 소비 이벤트 루프가 대기 중 채널이 닫히는 경우에도 종료를 감지하고 복구 또는 실패 처리를 시작합니다. ACK·NACK 시점에 발생하는 오류에만 의존하지 않음을 테스트로 확인합니다. |
| AC-05 | ACK timeout 장애 로그에서 일반 연결 장애와 원인을 구분할 수 있고, 관련 큐와 timeout 초과 사실을 확인할 수 있습니다. |
| AC-06 | 비복구 장애 및 복구 한도 초과가 Worker 실패로 전파됩니다. Worker의 실패 전파가 이전 ThreadPool 작업 완료를 기다리지 않으며, Python 프로세스 자체의 강제 종료 보장과 구분됨을 검증합니다. |
| AC-07 | 기존 RabbitMQ Consumer·Worker 테스트와 새 장애·복구 테스트가 통과하고, Redis 소비 및 정상 Worker 종료 동작에 회귀가 없습니다. |
| AC-08 | 실제 브로커 검증을 수행한 경우에만 그 결과를 Mock 테스트와 구분해 기록합니다. 실행하지 않은 RabbitMQ 장애 주입이나 프로세스 종료 검증은 통과한 것으로 보고하지 않습니다. |
| AC-09 | 공개 설정이나 운영 동작이 바뀌면 한국어·영어 매뉴얼의 설명과 예제가 서로 일치하고 구현된 계약을 정확히 반영합니다. |
| AC-10 | 복구 전후 Pool 객체의 동일성이 유지되고 내부 실행기는 교체됩니다. ProcessPool의 이전 작업 프로세스 종료와 ThreadPool의 이전 작업 완료 후 스레드·관련 자원 정리를 각각 검증합니다. 이전 미실행 작업은 실행되지 않아야 합니다. |
| AC-11 | 종료되지 않은 이전 ThreadPool 작업이 있는 동안에도 새 실행기가 작업을 받을 수 있습니다. 같은 메시지의 중복 실행 가능성을 수용하되, 이전 작업이 끝난 뒤 새 실행기를 종료하거나 오염시키지 않음을 확인합니다. |

| 항목 | 확인할 내용 |
| --- | --- |
| 복구 설정 | Worker의 keyword-only `recovery_attempts=5`, `recovery_interval=60`으로 제공합니다. 횟수는 음수 아닌 정수이고 `0`이면 복구하지 않습니다. 간격은 초 단위의 유한한 음수 아닌 수이며 두 값 모두 `bool`은 거부합니다. 첫 시도는 즉시 실행하고 전체 구독 복원 성공 시 다음 장애의 한도를 초기화합니다. |
| 복구 대상 | 연결 계층 AMQP 오류, 브로커 연결·채널 종료 코드 `320`·`541`, ACK timeout `406`, 명시적 stop 없는 소비 루프 종료를 복구합니다. 인증·권한·프로토콜 불일치, 큐 부재·다른 `406`, 사용자 handler·decode 오류는 재시도하지 않습니다. 최초 연결·구독 단계의 오류는 기존처럼 전파합니다. |
| 실행기 생명주기 | DefStream ThreadPool·ProcessPool과 DefStream Executor를 사용하는 Pool을 지원합니다. 사용자 지정 executor의 복구는 명시적 오류로 거부합니다. Python 3.9 이상에서 공개 multiprocessing Process API로 소유 프로세스를 추적·종료하며, 실행 단위의 setup·cleanup 오류 전파를 유지합니다. 강제 종료한 프로세스의 cleanup 완료는 보장하지 않습니다. |

복구 지원 여부는 `@runtime_checkable`을 적용한 `Recoverable` Protocol의 `is_recoverable(error: BaseException) -> bool` 계약으로 판별합니다. 별도 지원 플래그나 기본 Consumer의 기본 구현은 두지 않습니다. 현재 브로커 구현 중 RabbitMQ Consumer가 이 계약을 제공하며 Redis 등 미지원 Consumer의 기존 실패·종료 경로는 유지합니다. ACK timeout 로그의 구독 큐 목록은 공유 채널에 영향받는 큐들이며, 브로커 사유에 정보가 없다면 특정 작업이 원인이라고 단정하지 않습니다.

PR 리뷰에 따른 기존 계약의 보완 사항은 다음과 같습니다.

- ProcessPool은 종료 대기 중 비정상 종료도 감지하고, 생존 프로세스를 회수한 뒤 미완료 Future를 실패 처리합니다. 정상 종료 알림을 보낸 프로세스는 비정상 종료로 분류하지 않습니다.
- 소비 시작 직전의 stop 요청을 놓치지 않아야 합니다.
- 복구 가능한 Consumer·브로커 정리 오류는 로그를 남기되 재연결 시도 자체를 차단하지 않습니다. 복구 불가능한 오류는 전파합니다.
- 사용자 지정 executor의 재생성은 지원하지 않지만 실패 종료에서는 `shutdown(wait=False)`를 요청합니다. 비복구 오류·복구 비활성화의 원래 예외를 종료 미지원 오류로 대체하지 않습니다.

## 검증 범위와 제한

- 단위 테스트에서 복구 횟수, 예외 분류, 채널·연결 재생성, QoS와 구독 복원, 정상 `stop()` 구분, 오래된 delivery tag 차단 및 로그를 검증합니다.
- Worker 복구 테스트에서 Pool 객체 유지·내부 실행기 교체, 설정한 복구 횟수·간격과 이전 콜백 격리를 검증합니다. 대기 간격은 제어 가능한 시간 수단으로 검증하며 실제로 여러 분을 기다리는 테스트를 강제하지 않습니다.
- 실제 실행기를 사용하는 제한된 테스트로 ProcessPool의 이전 프로세스 종료와 ThreadPool의 이전 작업 완료 후 자원 정리를 확인합니다. 복구 실패의 전파와 프로세스 종료 보장은 구분합니다.
- 실제 RabbitMQ 장애 주입은 별도의 통합 검증으로 구분합니다. 브로커 버전·장애 조건·실제 실행 여부가 확인되지 않으면 운영 동작을 보장한다고 보고하지 않습니다.
- 재전달 메시지와 이전 작업의 중복 실행 가능성은 남습니다. 호출자 측 멱등성은 본 요구사항의 검증 대상이 아닙니다.
