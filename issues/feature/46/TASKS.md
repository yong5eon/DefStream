# 요구사항 분석·정의 결과

이슈 원문과 RabbitMQ Consumer·Worker·Pool의 현재 동작을 대조하고 [요구사항 명세](./REQUIREMENTS.md)를 작성했습니다. 이후 사용자 확인에 따라 별도 supervisor 없이 Worker 내부에서 기존 Pool 객체를 유지하고 내부 실행기와 브로커 연결을 복구하는 방향으로 갱신했습니다.

복구 한도와 시도 간 고정 간격은 설정 가능하며 기본값은 5회·1분입니다. ProcessPool의 이전 작업 프로세스는 종료하고 ThreadPool의 이전 작업은 완료를 기다리지 않되, 작업 완료 후 이전 스레드와 자원을 정리합니다. 이전 콜백은 새 실행기·Consumer의 상태에서 격리합니다. 남은 스레드의 중복 실행·외부 부작용·자원 점유와 프로세스 종료 지연 가능성은 수용한 제한입니다.

[작업 계획](./PLAN.md)에 선행 결정, 실행기 생명주기·소비 장애 감지·Worker 복구의 구현 순서, 인수 기준별 검증 및 매뉴얼 갱신을 정리했습니다. 첫 복구 시도의 대기 여부와 횟수 초기화 등은 확정된 것으로 처리하지 않고 선행 결정으로 남겼습니다.

구현 후 검증에서 복구 전용 17개와 최종 기능 회귀 294개 중 279개가 통과하고 15개는 생략됐습니다. 새 프로세스 경로의 setup·cleanup 예외 전파 누락을 검증 중 발견해 수정했습니다. 전체 discovery에서 패키징 메타데이터 파일 목록 검사 3건이 실패했으며, 변경하지 않은 설치·작업트리 메타데이터가 wheel 경로와 다른 환경임을 확인했습니다.

구현 내용은 [구현 종합](./IMPLEMENTS.md), 실행 명령·인수 기준과 제한은 [최종 검증 기록](./tasks/1793275501812.md)을 참고하세요. 실제 RabbitMQ·Redis 서버 장애 주입과 모든 지원 Python 버전 검증은 수행하지 않았습니다. 커밋·푸시·PR 생성은 하지 않았습니다.
