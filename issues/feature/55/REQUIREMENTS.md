# Worker 메시지 발행·요청 재시도 요구사항

## 목적

Worker의 `emit()`과 `request()`에 선택적 재시도를 추가하여 브로커 호출 실패를 설정된 횟수까지 다시 시도합니다. 이슈 원문과 작업 브랜치 정보는 [이슈 기록](./README.md)을 기준으로 합니다. 이 문서는 요청 내용과 현재 구현을 대조한 분석 및 목표 동작을 정의하며, 구현·검증 결과는 아직 포함하지 않습니다.

## 분석과 근거

### 이슈에서 요청한 결과

- `emit()`과 `request()`에서 최대 재시도 횟수와 시도 간 대기 시간을 선택적으로 지정합니다.
- 기본 최대 재시도 횟수는 `None`으로, 재시도하지 않고 기존처럼 한 번만 호출합니다. 기본 대기 간격은 1초입니다.
- 재시도 횟수는 최초 호출 이후의 추가 시도 횟수입니다. 실패 후 다음 시도가 있을 때만 대기하고, 성공하면 즉시 반환하며, 마지막 실패 뒤에는 대기하지 않습니다.
- 모든 시도가 실패하면 마지막 호출에서 난 예외를 그대로 전파합니다.
- 기존 `request()`의 `timeout`, `priority` 전달과 Worker 계층에서 재시도를 제공한다는 범위를 유지합니다.

### 현재 코드와 요구사항의 차이

- [Worker 메시지 함수](../../../src/Worker/Message.py)의 `emit()`은 작업·본문·브로커 기능·우선순위를 확인한 뒤 `broker.emit()`을 한 번 호출합니다. `request()`도 같은 순서로 입력을 확인한 뒤 `broker.request()`를 한 번 호출하고, 매번 기존 `timeout`을 전달합니다.
- 입력 검증과 지원 기능 확인은 브로커 호출보다 앞서 수행됩니다. 재시도는 브로커 메서드 호출에만 적용하고, 이 검증을 반복하거나 `NotImplementedError`를 재시도 대상으로 만들 필요는 없습니다.
- 공통 [브로커 연결 계약](../../../src/Broker/Connection.py)은 발행·요청 지원 여부를 Protocol로 표현하지만, 재시도 가능한 예외를 공통 분류하는 계약은 없습니다. 이슈의 요청대로 재시도 동작은 Worker API 계층에 둡니다.
- `request()`를 지원하지 않는 연결은 `Requestable` 검사에서 브로커 I/O 전에 거부됩니다. Redis 연결은 현재 `Requestable`을 구현하지 않습니다.
- RabbitMQ의 [RPC 응답 처리](../../../src/Broker/Implements/RabbitMQ/Queue.py)는 원격 작업 오류 응답을 `RemoteError`로 던집니다. 사용자는 재시도 범위에 브로커 호출에서 발생하는 모든 예외를 포함하도록 확정했습니다. 따라서 `RemoteError`도 재시도되며, 실패한 원격 작업이 다시 실행될 수 있습니다.
- 기존 [작업 메시지 테스트](../../../tests/test_task_messages.py)는 Mock 브로커로 Worker 함수의 호출 횟수·인자·오류 전파를 검증할 수 있습니다. 실제 브로커에 의존하지 않고 재시도 횟수와 대기를 검증할 수 있습니다.
- [작업 매뉴얼](../../../docs/Tasks.md)과 영어판은 현재 소비 메시지의 오류 정책·재전달을 설명합니다. 새 API 재시도와 소비자 재전달이 서로 다른 동작임을 구분하여 두 문서를 함께 갱신해야 합니다.

## 확정 요구사항

| ID | 요구사항 |
| --- | --- |
| R-01 | `emit()`과 `request()`에 `retry`와 `interval` 키워드 인자를 제공해야 합니다. 기본값은 각각 `None`과 1초입니다. |
| R-02 | `None` 또는 `0`회 재시도는 최초 호출만 수행합니다. `N`회 재시도는 최초 호출 후 최대 `N`회 추가 호출까지 허용합니다. |
| R-03 | 최초 호출은 대기 없이 수행합니다. 실패 후 재시도가 남은 경우에만 지정 간격을 기다립니다. 성공하면 즉시 반환하고, 마지막 실패 후에는 대기하지 않습니다. |
| R-04 | 브로커의 `emit()` 또는 `request()` 호출이 예외를 던지면 재시도 정책을 적용합니다. 사용자가 확정한 범위에는 `RemoteError`를 포함한 브로커 호출의 모든 일반 예외가 포함됩니다. 입력·작업 검증 및 기능 지원 확인 단계에서 발생하는 오류는 재시도하지 않습니다. |
| R-05 | 어느 시도에서든 성공하면 해당 호출의 기존 반환값을 그대로 반환합니다. 모든 시도가 실패하면 마지막 시도의 예외 객체와 타입을 바꾸지 않고 전파합니다. |
| R-06 | `request()`의 기존 `timeout`은 각 재시도 호출에 동일하게 전달합니다. 재시도 전체 시간에 대한 별도 총 timeout은 추가하지 않습니다. 기존 `priority`, 본문과 작업 매개변수 전달도 유지합니다. |
| R-07 | 재시도는 `DefStream.Worker`의 `emit()`·`request()`에만 적용합니다. 브로커 Protocol·구현체에는 재시도 설정이나 중복 재시도를 추가하지 않습니다. |
| R-08 | 기존 동작을 유지하면서 재시도가 기본 비활성화된 선택 기능으로 동작해야 합니다. 입력 검증·브로커 소유권·연결 수명주기 계약은 바꾸지 않습니다. |
| R-09 | 문서에서 `emit()`/`request()` 호출 재시도와 소비 중 메시지 오류·재전달 정책을 구분하고, 이미 처리된 발행·요청이 다시 전송될 수 있음을 안내합니다. |

## 구체화한 구현 계약

- `retry`는 `None` 또는 `bool`이 아닌 0 이상의 정수입니다. 다른 타입은 `TypeError`, 음수는 `ValueError`로 거부합니다.
- `interval`은 `bool`이 아닌 유한한 0 이상 `threading.TIMEOUT_MAX` 이하의 정수 또는 실수입니다. 타입이 맞지 않으면 `TypeError`, 범위 밖 값이나 비유한 값은 `ValueError`로 거부합니다. 큰 정수의 실수 변환 오버플로를 피하도록 범위를 먼저 확인하며, 두 인자의 유효성은 브로커 메서드 호출 전에 검사합니다.
- `RemoteError`까지 재시도하면 원격 작업 오류 응답을 받은 경우에도 해당 요청을 다시 실행할 수 있습니다. 이 동작은 사용자가 선택한 예외 범위에 따른 의도된 결과이며, 멱등성이나 중복 방지는 이 요구사항에 포함되지 않습니다.

## 인수 기준

아래 기준은 구현 완료 후 확인했으며, 검증 범위와 미실행 항목은 [작업 종합](./TASKS.md)에 기록합니다.

| ID | 검증 기준 |
| --- | --- |
| AC-01 | 기본값에서는 `emit()`과 `request()`가 한 번만 호출되고 재시도 대기가 없습니다. |
| AC-02 | 재시도 횟수 `0`은 한 번, `N`은 최대 `N + 1`번 호출합니다. |
| AC-03 | 계속 실패하는 `N`회 재시도는 `N`회 대기만 수행하며, 마지막 실패 후에는 대기하지 않습니다. |
| AC-04 | 중간 시도에서 성공하면 반환값을 보존하고 후속 호출·대기를 하지 않습니다. |
| AC-05 | 계속 실패하면 마지막 예외 객체를 그대로 전파합니다. `RemoteError`도 지정 횟수까지 재시도합니다. |
| AC-06 | 두 함수의 재시도에서 `priority`·요청 `timeout`·본문·작업 매개변수 전달이 기존 계약과 일치합니다. |
| AC-07 | 작업·본문·브로커 기능 검증 실패는 브로커 메서드를 호출하지 않고 재시도도 하지 않습니다. |
| AC-08 | 단위 테스트에서 실제 대기 없이 기본·사용자 지정 간격과 정확한 대기 횟수를 검증합니다. |
| AC-09 | 한국어·영어 작업 매뉴얼에 공개 API, 사용 예, 기본 동작 및 중복 실행 주의사항을 일관되게 반영합니다. |

## 범위 제외

- 브로커별 재시도, 오류 종류별 backoff·jitter, 재시도 전체 deadline, 자동 연결 재생성은 추가하지 않습니다.
- 멱등 키, 중복 요청 제거, exactly-once 처리 또는 중복 실행 방지는 보장하지 않습니다.
- 소비자 측 ACK·NACK·메시지 재전달 정책은 변경하지 않습니다.
