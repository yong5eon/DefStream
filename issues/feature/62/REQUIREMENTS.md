# Connection 기반 선택적 타이머 요구사항

## 목적과 범위

[원본 이슈와 작업 정보](./README.md)를 기준으로, 연결 구현체가 제공하는 타이머를 공통 계약으로 이용한다. 이번 범위는 Connection을 이용하는 `SetTimer`, `Timer`, `TimerCallback`과 이를 지원하는 RabbitMQ 연결 구현, 직접 관련된 테스트·문서로 한정한다.

Consumer의 인터페이스·구현과 Worker·Ping·Executor 등 다른 구성 요소는 변경하지 않는다. 앞서 논의한 리팩터링은 후속 작업으로 분리한다.

이번 문서는 요구사항 분석과 명세이다. 구현 순서와 검증 방법은 [작업 계획](./PLAN.md)에 정리하며, 제품 코드는 아직 변경하지 않았다.

## 분석 근거와 현재 동작

- [Connection](../../../src/Broker/Connection.py)은 연결의 기본 계약과 `GetExchange`, `GetQueue`, `GetStream`, `GetConsumer` 등 선택적 기능의 프로토콜을 구분한다. 타이머도 모든 연결에 강제하지 않고 같은 방식으로 분리한다.
- [RabbitMQ Consumer](../../../src/Broker/Implements/RabbitMQ/Consumer.py)는 이미 Pika의 `call_later`와 `remove_timeout`으로 내부 확인용 타이머를 관리한다. 소비 루프의 `finally`에서 해당 타이머를 취소한다.
- 기존 Consumer의 타이머와 종료 처리는 변경하지 않는다. 새 예약의 등록·취소는 연결 객체를 통해 제공하며 소비자별 예약 관리 기능은 추가하지 않는다.

## 원문과 대화에서 변경한 사항

- 원문은 소비자 API를 통한 타이머 지원을 제안했지만, 대화에서는 연결 객체의 선택적 `SetTimer` 프로토콜로 제공하기로 확정했다.
- 프로토콜과 반환 핸들·콜백의 명칭은 `SetTimer`, `Timer`, `TimerCallback`으로 확정했다.
- 앞서 논의한 Consumer의 `complete`, `fail`, `call` 제거와 `close` 추상 메서드 선언은 이번 요구사항에서 철회했다. 기존 선언·구현·호출 흐름을 그대로 유지한다.
- 원문의 소비 종료 시 예약 정리는 이번 범위에서 제외한다. 타이머 수명주기와 적절한 취소 시점은 호출자와 기반 구현이 관리하며, 별도 자동 정리 계층을 추가하지 않는다.

## 확정 요구사항

### R1. 선택적 타이머 등록

- [연결 계약 모듈](../../../src/Broker/Connection.py)에 별도 `SetTimer` 프로토콜을 정의한다. 기본 `Connection`과 Consumer에는 타이머 등록을 필수 계약으로 추가하지 않는다.
- 지원하는 연결 구현체가 지연 시간과 콜백을 받아 일회성 예약을 등록하고 `Timer` 핸들을 반환한다. 타이머의 구현 방식은 각 연결 구현체에 맡긴다.
- 우선 RabbitMQ 연결에서 구현한다. Redis 등 다른 연결에는 타이머 구현이나 미지원 예외 메서드를 강제하지 않는다.
- 이번 RabbitMQ 구현은 Pika의 내부 타이머를 사용한다. 별도 타이머 스레드나 범용 스케줄러를 추가하지 않으며, 호출자가 Pika 연결 객체나 타이머 ID를 직접 다루지 않게 한다.

### R2. 타이머 핸들과 콜백

- `Timer`는 내부 구현을 숨기는 반환 핸들의 프로토콜이며, 공개 기능은 `remove() -> None`으로 한정한다.
- `remove`는 아직 실행되지 않은 예약을 취소한다. 실행 중인 콜백을 강제로 중단하는 기능은 포함하지 않는다.
- 실행 완료·중복 취소 여부를 이유로 자체 오류나 별도 상태 관리 계층을 추가하지 않는다. 취소 동작과 오류는 기반 타이머 API를 따른다.
- `TimerCallback`은 인자 없이 실행되며 반환값이 없는 `__call__() -> None` 계약이다.
- 반복 실행은 콜백에서 다음 타이머를 등록하는 방식으로 지원한다. 별도 반복 타이머 API, 재설정, 상태 조회 기능은 요구하지 않는다.

등록과 반환 타입의 계약은 다음과 같이 확정한다. 아래 코드는 구현할 계약의 명세이며, 현재 제품에 추가된 코드는 아니다.

```python
from abc import abstractmethod
from typing import Protocol, runtime_checkable


@runtime_checkable
class Timer(Protocol):
  @abstractmethod
  def remove(self) -> None: ...


class TimerCallback(Protocol):
  def __call__(self) -> None: ...


@runtime_checkable
class SetTimer(Protocol):
  @abstractmethod
  def set_timer(self, cb: TimerCallback, seconds: int) -> Timer: ...
```

- 등록 메서드는 `set_timer`이며, 인자 순서는 `cb`, `seconds`이다.
- 두 인자는 기본값 없이 필수로 받으며, 위치 인자 또는 `cb=`, `seconds=` 키워드 인자로 전달할 수 있다.
- `seconds`의 타입은 `int`, 단위는 초이며 반환 타입은 `Timer`이다.
- `Timer`, `SetTimer`에는 `@runtime_checkable`을 적용하고, 각각 `remove`, `set_timer`에 `@abstractmethod`를 적용한다. `TimerCallback`에는 이 두 데코레이터를 추가하지 않는다.

### R3. 기반 구현의 동작 이용

- 지연 시간은 등록 시점부터 초 단위로 계산한다. 소비 루프 시작에 맞춰 예약을 연기하거나 재등록하지 않는다.
- RabbitMQ는 Pika의 타이머 등록·취소 API에 위임한다. 이벤트 처리가 진행되면 메시지가 없어도 연결 소유 스레드에서 콜백이 실행된다. 긴 처리 등에 따른 실행 지연은 기반 구현의 동작을 따른다.
- 등록·취소 가능한 시점, 스레드 제약, 연결 종료 후 동작은 기반 API의 계약을 따르며 호출자가 이에 맞춰 사용한다. 완전한 스레드 안전성을 독자적으로 보장하는 동기화·전달 계층을 추가하지 않는다.
- 타이머 목록·종료 상태를 별도로 추적하여 자동 취소하는 기능을 요구하지 않는다. 새 타이머를 위해 Consumer나 연결의 종료 처리를 변경하지 않는다.
- 이미 실행·취소된 핸들, 종료된 연결의 취소, 음수·0초 지연의 처리는 기반 API에 맡긴다. 자체 입력 검증·기본값·폴백을 추가하지 않으며 발생한 오류를 숨기지 않는다.
- 콜백 예외는 기반 타이머의 이벤트 처리 경로를 통해 드러나게 한다. 별도로 잡아서 무시하거나 정상 종료로 바꾸지 않는다.

### R4. 기존 코드와의 경계

- Consumer의 `complete`, `fail`, `call`, `close`, `run` 등 인터페이스와 구현은 변경하지 않는다.
- Worker·Ping·Pool·Executor·Event의 구현 및 호출 흐름을 변경하지 않는다.
- 타이머 추가를 이유로 ACK·NACK·RPC·중단·복구 처리나 프로세스 시작 방식을 리팩터링하지 않는다.
- 기존 구독·소비 순서·소유 스레드 전달·연결 소유권을 유지한다.

### R5. 사용 문서

- 관련 한국어·영어 매뉴얼에 지원 범위, 등록 시점 기준의 초 단위 시간, 실행 지연 가능성, 등록·취소, 재등록 예시와 기반 API의 사용 제약을 반영한다.
- Connection을 이용하는 선택적 기능으로 설명하고 Consumer 종료 시 자동 취소를 보장하지 않음을 명시한다. 아직 구현하지 않은 API를 사용 가능한 기능으로 안내하지 않는다.

## 계약 확정 결과

1. 등록 계약은 위 R2의 `set_timer(self, cb: TimerCallback, seconds: int) -> Timer`로 확정했다.
2. 지연 시간은 등록 시점부터 계산한다. 등록 가능한 시점은 기반 구현을 따른다.
3. 타이머의 수명주기와 취소 시점은 호출자와 기반 구현의 책임이다. 별도 연결 종료·오류 정리 기능을 추가하지 않는다.
4. 스레드 제약은 기반 구현을 따른다. 공통 프로토콜이나 래퍼에서 추가 스레드 안전성을 보장하지 않는다.
5. 중복 취소·종료된 연결·음수·0초 등의 동작은 기반 API에 맡긴다. 이 차이를 통일하기 위한 자체 상태 관리·검증을 추가하지 않는다.

## 인수 기준과 검증 범위

| 기준 | 검증 내용 |
| --- | --- |
| 선택적 기능 | RabbitMQ 연결의 타이머 지원과 기본 Connection·Consumer 및 Redis에 타이머 의무가 없음을 확인 |
| API 계약 | 확정한 시그니처·데코레이터, 위치·키워드 인자 호출과 반환 핸들의 계약 확인 |
| 유휴 실행 | 메시지가 없는 실제 소비 대기 중 콜백 실행 및 메시지 처리와 소유 스레드 일치 확인 |
| 등록·취소 위임 | 등록 시점의 지연 시간이 기반 타이머에 전달되고 remove가 기반 취소 API에 위임되는지 확인 |
| 반복·예외 | 콜백 재등록에 의한 반복 실행 및 콜백 예외의 소비 루프 전파 확인 |
| 변경 경계 | Consumer·Worker·Ping·Pool·Executor·Event 및 Redis 구현이 수정되지 않았음을 확인 |
| 회귀 | 연결 타이머 관련 테스트와 직접 영향받는 기존 검증으로 소비·연결 동작 유지 확인 |
| 문서 | 확정 API와 한국어·영어 예제, 지원 범위·제약 및 호환성 안내의 일치 확인 |

위 항목은 향후 구현 검증 기준이며, 현재 제품 테스트를 실행하거나 기능 구현을 완료한 것은 아니다.

## 제외 범위

- HTTP·SSE 프로토콜 및 연결 유지용 출력 자체의 구현
- Redis 타이머 지원 추가와 모든 브로커에 대한 스케줄러 제공
- 별도 타이머 스레드, 범용 작업 스케줄러, 실시간 실행 보장
- Consumer 인터페이스 정리, `complete`·`fail`·`call` 제거 및 `close` 추상 메서드 선언
- Worker·Ping·Pool·Executor·Event 리팩터링, 실행기 교체와 프로세스 시작 방식 변경
- 소비자별 타이머 소유권 관리와 소비 종료 시 새 예약의 자동 취소
- 타이머 수명주기의 별도 추적·자동 정리, 추가 스레드 동기화 및 기반 API와 중복되는 입력·상태 검증
