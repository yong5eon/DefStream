# 워커 작업 우선순위 지원 요구사항

## 1. 목적

워커 작업의 기본 우선순위를 정의하고, 큐 선언과 메시지 전송 및 RPC 요청에
이를 반영할 수 있도록 한다. 우선순위의 실제 처리는 지원 브로커에 위임한다.

본 문서는 구현 전 요구사항 명세이다. 확정된 설정 및 검증 정책은 9절에 기록한다.

## 2. 범위

### 포함

- 작업 정의 시 기본 메시지 우선순위와 큐의 우선순위 설정 정의.
- `declare`에서 작업의 큐 우선순위 설정을 지원 브로커에 전달.
- `send` 및 RPC 요청에서 호출별 메시지 우선순위 지정.
- 브로커 지원 여부 확인 및 오류 처리.
- 공통 계약, 관련 테스트, 사용자 문서와 예제 갱신.

### 제외

- Redis 우선순위 큐 구현과 Redis RPC 기능 추가.
- 실행 중인 작업의 선점 및 워커 실행 풀의 우선순위 스케줄링.
- 서로 다른 큐 사이의 전역 우선순위.
- 낮은 우선순위 작업의 기아 방지를 위한 에이징 및 가중 스케줄링.

## 3. 용어 및 현재 API

| 용어 | 의미 |
|---|---|
| `priority` | 개별 메시지의 우선순위. 숫자가 클수록 먼저 전달할 대상이다. |
| 기본 우선순위 | 작업 정의에 지정하고 호출에서 생략했을 때 사용하는 메시지 우선순위. |
| `max_priority` | 큐가 지원할 최대 우선순위. 메시지 우선순위와 구분되는 선언 설정이다. |
| 대기 메시지 | 브로커에 남아 있고 소비자에게 아직 전달되지 않은 메시지. |

현재 워커 공개 API의 RPC 이름은 `request`이고, RabbitMQ 큐의 저수준 RPC
API 이름은 `call`이다. 본 요구사항의 RPC 지원은 두 경로를 모두 포함하되,
기존 이름 변경이나 새 `call` 별칭 추가를 요구하지 않는다.

기본 우선순위와 최대 우선순위는 모두 작업의 `parameters`에 지정하는 브로커별
구독 설정으로 관리한다. RabbitMQ의 기존 `Subscription`에 `priority`와
`max_priority`를 함께 정의하며, `Run`에 별도의 기본 우선순위 속성이나 선언
키워드를 추가하지 않는다. 구독 객체와 대응하는 매핑 입력을 모두 지원한다.
브로커 인스턴스에 작업별 최대 우선순위를 별도로 중복 설정하지 않는다.

## 4. 기능 요구사항

| ID | 요구사항 |
|---|---|
| WPRI-01 | 구체적인 워커 작업의 구독 설정에 기본 메시지 우선순위 `priority`를 지정할 수 있어야 한다. RabbitMQ는 `Subscription.priority`를 사용한다. |
| WPRI-02 | 작업에 큐의 우선순위 지원 설정과 최대 우선순위를 정의할 수 있어야 한다. 기본 메시지 우선순위와 최대 우선순위는 서로 구분해야 한다. |
| WPRI-03 | `declare(task=..., broker=...)`는 작업의 큐 우선순위 설정을 지원 브로커의 선언 경로에 전달해야 한다. 기본 메시지 우선순위만 선언 인자로 전달하는 것으로 대체해서는 안 된다. |
| WPRI-04 | `send`는 호출별 우선순위를 선택적으로 받을 수 있어야 한다. |
| WPRI-05 | `request`는 호출별 우선순위를 선택적으로 받고 RPC 요청 메시지에 적용해야 한다. RPC 응답 메시지의 우선순위 지정은 범위에 포함하지 않는다. |
| WPRI-06 | 유효 우선순위는 호출별 지정값, 작업 기본값, 기존 브로커 기본 동작 순으로 결정해야 한다. |
| WPRI-07 | `0`은 명시적인 우선순위로 취급해야 한다. 미지정 상태를 판단할 때 참·거짓 검사로 `0`을 누락해서는 안 된다. |
| WPRI-08 | 우선순위 설정을 상속하고 유효한 값으로 재정의할 수 있어야 한다. 자식 작업에서 상속받은 기본·최대 우선순위 설정을 해제할 수 없어야 한다. |
| WPRI-09 | 우선순위는 작업 본문과 분리된 메시지 메타데이터로 전달해야 한다. 작업의 요청 스키마나 `run` 인자를 변경해서는 안 된다. |
| WPRI-10 | 공통 브로커 계약은 우선순위 지원 여부를 구별할 수 있어야 한다. 우선순위를 사용하지 않는 기존 브로커에 새 필수 인자나 구현 의무를 부과해서는 안 된다. |

## 5. 검증 및 미지원 브로커 처리

| ID | 요구사항 |
|---|---|
| WPRI-11 | 메시지 우선순위와 최대 우선순위는 정수로 검증해야 하며, Python의 `bool`은 허용하지 않아야 한다. |
| WPRI-12 | 브로커의 허용 범위를 벗어나는 값은 발행·선언 전에 명확한 오류로 처리해야 한다. |
| WPRI-13 | 작업의 유효 최대값이 있으면 브로커의 허용 범위 안에 있는지 검증하고, 기본값과 호출별 메시지 우선순위가 유효 최대값을 초과하면 거부해야 한다. 작업의 기본·최대값 없이 호출에서만 지정하면 브로커 범위만 검증한다. `send`와 RPC 요청은 전달받은 작업 및 브로커를 기준으로 발행 전에 검증해야 한다. |
| WPRI-14 | 우선순위를 사용하지 않으면 Redis를 포함한 기존 브로커 호출을 그대로 유지해야 한다. |
| WPRI-15 | Redis 등 미지원 브로커에 큐 우선순위 설정이나 유효 메시지 우선순위가 지정되면 `NotImplementedError`로 지원 불가를 명시해야 한다. 지정값을 조용히 무시하거나 우선순위 없이 발행해서는 안 된다. |
| WPRI-16 | 잘못된 타입·값 및 설정 충돌은 기존 오류 처리 방식에 맞춰 `TypeError` 또는 `ValueError`로 구분하고 원인을 설명해야 한다. |

## 6. 동작 보장과 호환성

- 우선순위는 같은 큐의 대기 메시지 전달 순서에 적용한다.
- 이미 소비자에게 전달되었거나 실행 중인 작업을 중단하거나 재정렬하지 않는다.
- 여러 워커, prefetch, 재전달이 있으면 실행 시작 및 완료 순서는 우선순위와
  다를 수 있다. 높은 우선순위 작업의 완료 순서를 보장하지 않는다.
- 동순위 메시지의 전달 순서는 브로커가 제공하는 보장 범위를 따른다.
- 우선순위를 설정하지 않은 작업의 선언, 전송, RPC 및 오류 처리는 기존과
  동일하게 유지한다.
- 워커의 ACK, NACK, 실패 정책, 요청·응답 스키마, 타임아웃 동작을 보존한다.
- 공통 워커에서 우선순위를 흉내 내기 위한 별도 로컬 대기열을 추가하지 않는다.

## 7. 인수 기준

| ID | 검증 시나리오 및 기대 결과 |
|---|---|
| WAT-01 | 최대 우선순위가 정의된 작업에서 호출별 우선순위를 생략한 `send`와 `request`가 작업 기본 우선순위를 지원 브로커에 전달한다. |
| WAT-02 | 호출별 우선순위가 작업 기본값을 덮어쓰며, 호출값 `0`도 보존된다. |
| WAT-03 | 작업 우선순위 설정이 없는 기존 호출은 기존 브로커 메서드의 인자 형태와 동작을 유지한다. |
| WAT-04 | `declare`가 메시지 우선순위와 구분된 큐 선언 설정을 전달한다. |
| WAT-05 | 잘못된 타입, `bool`, 음수, 브로커 허용 범위 초과 및 작업 최대값 초과가 거부된다. |
| WAT-06 | 미지원 브로커에 우선순위가 지정되면 브로커 선언·발행 전에 명확히 실패한다. 미지정 시 기존 호출은 성공한다. |
| WAT-07 | 작업 정의의 설정 상속 및 유효한 값으로의 재정의가 동작하며, 자식 작업에서 설정을 해제할 수 없다. |
| WAT-08 | 우선순위 설정 전후 작업 본문과 요청·응답 스키마의 입력값이 동일하다. |
| WAT-09 | 기존 워커 및 RPC 관련 테스트가 계속 통과한다. |
| WAT-10 | 작업에 기본 우선순위만 정의하면 브로커 허용 상한을 유효 큐 최대값으로 사용한다. RabbitMQ에서는 `255`로 선언하고 전송 검증에도 같은 값을 사용한다. 기본값 `0`도 이 규칙을 적용한다. |
| WAT-11 | 작업에 최대 우선순위만 정의하면 기본 우선순위는 `None`이며, 호출별 값도 없으면 메시지 우선순위 속성을 생략한다. 호출별 값이 있으면 작업 최대값으로 검증한다. |
| WAT-12 | 작업의 기본·최대 우선순위 없이 호출에서만 지정하면 브로커 허용 범위로 검증하여 발행한다. 큐 자동 선언·재설정·서버 조회는 수행하지 않는다. |

## 8. 연계 명세

- [RabbitMQ 요구사항](../../../../DefStream-RabbitMQ/issues/feature/1/REQUIREMENTS.md)
- RabbitMQ의 큐 종류, 허용 범위, 선언 제약과 실제 전달 순서는 브로커 명세에서
  구체화한다.

## 9. 확정된 설정 및 검증 정책

1. 기본 우선순위와 큐 최대 우선순위는 작업 정의에 둔다. 최대값은 작업에서
   사용하는 브로커별 구독 설정으로 표현하며, 기본값도 같은 구독 설정에 둔다.
   RabbitMQ의 기존 `Subscription`에 두 값을 함께 정의한다.
2. `declare`는 작업 정의의 구독 설정을 읽어 그 최대값으로 큐를 생성한다.
   작업 기본 우선순위가 정의되어 있고 최대값이 없으면 브로커 허용 상한을
   유효 큐 최대값으로 사용한다. RabbitMQ에서는 `255`이며, 기본값 `0`도 포함한다.
   호출별 메시지 우선순위만으로 큐 최대값을 자동 설정하지 않는다.
3. 호출별 우선순위를 생략하거나 `None`으로 전달하면 작업 기본값을 사용한다.
   명시적 `0`은 기본값을 덮어쓰는 유효한 값이다.
4. 자식 작업에서는 상속받은 우선순위 설정을 해제할 수 없다.
5. 브로커 자체의 허용 상한과 작업에 정의된 큐 최대값은 구분한다.
   RabbitMQ의 허용 상한은 `255`이며 작업 최대값도 이 범위 안에 있어야 한다.
   명시적 작업 최대값이 있으면 이를 우선 사용하며, 기본 우선순위만 정의한
   경우에는 2항에 따라 브로커 상한을 사용한다.
6. `send`와 RPC 요청은 작업과 브로커를 전달받아 유효 메시지 우선순위를
   유효 작업 최대값이 있으면 그 최대값 및 브로커 범위와 비교한다.
   서버 조회나 선언 이력 캐시는 필요하지 않다.
7. RabbitMQ는 기존 classic 큐 사용을 전제로 한다. 다른 큐 종류의 지원이나
   자동 판별을 이번 기능의 구현 요건으로 추가하지 않는다.
8. 작업에 최대 우선순위만 정의하면 기본 우선순위는 `None`이다.
   호출별 우선순위도 없으면 메시지 우선순위 속성을 생략한다.
   상속된 기본값이 있는 자식 작업은 이를 유지하며, 이 규칙으로 상속 설정을 해제하지 않는다.
9. 작업의 기본·최대 우선순위 없이 호출에서만 우선순위를 지정하는 것을 허용한다.
   이 경우 브로커 허용 범위만 검증하여 발행하고, 우선순위 큐의 사전 선언과
   실제 큐 최대값에 맞는 값 지정은 호출자 책임이다. 큐를 자동 변경하지 않으며,
   발행 성공만으로 실제 우선순위 전달을 보장하지 않는다.
